## New findings

### 1. P1 / small fix plus medium storage work: notification privacy can silently return to full previews

Three related failures are confirmed by the production preference hook and actual browser platform adapter:

- **Corrupt read:** set `slackoss:notification-previews` to malformed JSON, then mount the hook. It finishes loading with `unreadable: false`, `error: null`, and preview **`full`**. `notificationContent` therefore includes the synthetic private message. A generic platform that actually rejects the read instead yields **`none`** and an error, establishing the intended control.
- **Lost acknowledged choice:** initialize two distinct Platform instances before either saves. A saves account U1 as `none` and the persisted map confirms it. After delivering the storage event to the open second instance, B saves account U2 as `sender`. B writes only its stale map plus U2; U1's acknowledged `none` disappears. Reopening U1 yields **`full`**. This needs sequential writes, not a simultaneous-write race.
- **Stale open window:** A chooses `none`; B for the same account keeps **`full`** even after the storage event. It can continue constructing full notification content until reinitialized.

Cause: [notificationPreview.ts:100](../../../packages/ui/src/lib/notificationPreview.ts#L100) calls `storage.get` without strict mode. [platform.ts:362](../../../packages/ui/src/platform.ts#L362) turns browser read/JSON exceptions into null unless strict was requested; [notificationPreview.ts:140](../../../packages/ui/src/lib/notificationPreview.ts#L140) treats absent choices as full. [notificationPreview.ts:84](../../../packages/ui/src/lib/notificationPreview.ts#L84) writes a whole map captured by one Platform instance. The preference store has no cross-window subscription or transactional per-account merge.

**Approach:** request strict reads, validate the stored shape and keep the private fallback on unreadable data. Update one account through a shared storage transaction and subscribe every open window to authoritative changes, including failure/clear behavior. UI choices must describe the actual acknowledgement contract. Do not solve the whole-map overwrite with a reread followed by another unprotected whole-map write.

**Acceptance:** malformed JSON, wrong shapes and rejected reads display the private choice/error without message or sender details. Real independent tabs A/B save different accounts in both orders; both choices survive reopen. The same-account window observes a stricter choice before another notification is constructed. Rejected writes preserve the prior choice and offer a usable retry. Test plain-HTTP LAN and the desktop storage owner separately.

**Limits:** these diagnostics mount the real hook/adapter in jsdom and dispatch a browser-shaped storage event. No native OS notification or independent-tab transaction was exercised. The emitted-content observation calls the production content helper; it does not claim an actual notification was delivered.

**Additional product-browser confirmation:** the root-owned native T3 journey chose “Nothing about it” in the actual fresh production settings page and confirmed the synthetic account's persisted `none`. After replacing that fixture's saved preference map with malformed text and performing a full reload, the page selected “The message” without a read warning. [Browser state evidence](root-browser-notification.json) and [the captured settings screenshot](root-notification-after-corruption.png) independently confirm the browser reload/settings consequence. This journey did not deliver an OS toast or reproduce the two-window overwrite; those remain separate acceptance boundaries and are not counted among the 14 tests above.

### 2. P2 / medium: the client retains attachment URLs after deletion or some access revocations

With a real attached file cached, deleting its message removes that message from the timeline and fresh authenticated GET returns **404**. `client.files.peek/get` nevertheless returns the same local blob URL and the synthetic bytes remain readable. [workspace.ts:1160](../../../packages/client-core/src/workspace.ts#L1160) handles message deletion without invalidating its files; the cache's fast path at [fileCache.ts:96](../../../packages/client-core/src/fileCache.ts#L96) does not ask the server again.

With a real private-channel file cached, removing that account from the channel makes the channel disappear and GET returns **404**. When its timeline metadata has already gone, the cached URL also survives. [workspace.ts:979](../../../packages/client-core/src/workspace.ts#L979) discovers file IDs only through currently loaded timelines/thread pages; [fileCache.ts:10](../../../packages/client-core/src/fileCache.ts#L10) has no durable file-to-channel/message ownership index. The second probe deliberately removes history metadata directly to isolate this dependency; actual cache-eviction navigation was not replayed.

**Impact:** retained stale bytes and locally reusable URLs survive server removal. Already-downloaded bytes cannot be retroactively unrevealed, and this is **not a server authorization bypass**: both real endpoints correctly reject fresh access. We did not measure whether a currently visible lightbox displays denied content. Its state is separate from the timeline ([MessageTimeline.tsx:79](../../../packages/ui/src/components/MessageTimeline.tsx#L79)); a real component/browser acceptance should determine whether it remains open. For valid, unchanged authorization, reusing a cached attachment is useful and should remain.

**Approach:** record bounded message/channel ownership with cache entries independently of history. Purge downloaded URLs and cancel queued/in-flight transfers on file/message deletion, channel revocation and terminal auth changes even after metadata eviction. Notify active resource consumers so a known invalidation can close or explain an open lightbox. Account/workspace ownership must remain explicit; do not clear every valid file on an unrelated history eviction.

**Acceptance:** real deletion and real private access loss after actual history eviction invalidate their cached entries; pending transfers cannot reinstall them. Open previews/lightboxes close or show a clear unavailable state. Other still-authorized files remain usable and deduplicated; cache ownership metadata itself is bounded and cleared on destroy.

### 3. P3 / small: identical forward pagination is still repeated

Two concurrent `loadNewer` calls from the same seeded anchored window issue **two** actual HTTP requests and abort the first; only correct unique rows are installed. [workspace.ts:1808](../../../packages/client-core/src/workspace.ts#L1808) always begins a new ticket, while [workspace.ts:1643](../../../packages/client-core/src/workspace.ts#L1643) joins identical tail/older loads.

**Approach:** use the same shared request ownership for equivalent newer-page cursors, retaining replacement when the cursor/window differs. Check explicit canceled jumps as an adjacent lifecycle boundary before broadening the abstraction.

**Acceptance:** equivalent forward calls wait on one transfer and both settle; a changed window aborts the old one; live-event replay, order, uniqueness and visible anchoring stay correct. This is an API-level opportunity; no repeated-click browser journey or latency saving was established, so it follows the privacy and durability work.

## Scope decision, not an additional proven defect

An explicitly trusted alias of the same synthetic workspace changes its preview from `none` to `full`, because [notificationPreview.ts:58](../../../packages/ui/src/lib/notificationPreview.ts#L58) scopes by URL/user and does not use the authenticated workspace ID or approved address relationships. The settings say “For this workspace on this device” at [AccountDialog.tsx:659](../../../packages/ui/src/components/AccountDialog.tsx#L659). Decide whether the setting is per address or per authenticated workspace. For a workspace-wide promise, migrate it only across explicitly approved addresses and preserve account separation; default private while unknown. The probe uses real address-trust helpers with a synthetic identity, not live alias navigation.

# Tandem: phone participation, accessibility and personal trust

**Research and source access: September 25, 2026.** This extends the [product decision document](../../PRODUCT-RESEARCH-2026-09-25.md), [community research](../2026-09-24/community-research.md), [operations research](../2026-09-24/operations-research.md) and [roadmap](../../PRODUCT-ROADMAP-2026-09-24.md). It adds 25 registered sources, mostly platform documentation and standards, alongside a maintainer issue summary, a first-hand platform bug and a primary qualitative study. Some sources revisit standards already cited in the earlier review. Twenty-five URLs are not twenty-five independent observations.

**Main recommendation:** keep the PWA feasibility path, but measure installation, return, notification privacy and interrupted work as one phone journey. Bring accessible reading and multilingual composition into that slice. Define blocking across message requests, group invitations, notifications, calls and shared rooms before implementing individual controls. Native mobile remains conditional on an observed, important platform gap, particularly incoming-call behavior.

This is research and source inspection only. No real phones, assistive technologies, network fault tests, competitor applications or Tandem runtime flows were exercised in this pass. Proposed thresholds below are acceptance hypotheses chosen for an engineering pilot; they are not published platform guarantees, measured Tandem results, legal requirements or evidence of accessibility conformance. Existing draft state tables remain proposals and were not edited.

## 2. Update the PWA decision with newer platform evidence

### Installation and notifications are separate capabilities

The earlier review correctly identified iOS/iPadOS 16.4 Home Screen web push as the baseline platform path. Newer documentation changes two details. Safari 26's shipped release notes say websites added to the Home Screen open as web apps by default, with an “Open as Web App” choice. A manifest remains useful. Installation instructions must therefore be version-aware and should verify the resulting app mode rather than infer success merely from an icon. [P03: Safari 26 release](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)

Apple also documents Declarative Web Push for Home Screen apps on iOS/iPadOS 18.4 and Safari 18.5 on macOS. A browser can render a valid notification description and navigate from it without a service worker; optional worker processing can refine it. Apple describes fallback when that processing cannot run. This is an implementation option for a compatibility spike, not evidence that Tandem notifications are dependable. [P02: Apple WWDC25 session](https://developer.apple.com/videos/play/wwdc2025/235/)

WebKit still requires visible notifications for push; it does not permit silent push as an unrestricted synchronization channel. Its declarative design can fall back to the original description when optional processing fails. **Design consequence:** that original title/body must already satisfy the participant's privacy setting. Do not put sensitive message text in a fallback and depend on worker code to remove it. Do not use push events to silently maintain every workspace's unread count. [P01: WebKit design and behavior](https://webkit.org/blog/16535/meet-declarative-web-push/)

### A message acceptance receipt is not a person seeing a notification

RFC 8030 defines retention, urgency, replacement and subscription expiration. A service can shorten retention or expire a subscription; its acceptance of a push request cannot establish that a notification was seen. [P04: HTTP Web Push protocol](https://www.rfc-editor.org/rfc/rfc8030)

Proposed Tandem diagnostic states:

1. The workspace accepted the message.
2. A notification decision was made for a particular account/device.
3. The push provider accepted or rejected a request.
4. The app observed a delivery/click event, when its platform path exposes one.
5. The participant opened the conversation.

Do not collapse these into “delivered to Sam.” Some transitions are unobservable. Browser-rendered declarative push without executing app code makes that distinction particularly relevant. Store only short-lived operational identifiers needed to diagnose the path, without message text or full bearer-like subscription endpoints in routine logs.

Choose different expiry semantics for content classes. A persistent message can remain in server history after its notification expires; a call invite must not start ringing after its server deadline. Recheck the current authorization and current object state on tap. A notification about a removed message, expired guest session, deleted workspace or completed call should land on a comprehensible unavailable/ended state rather than another conversation with a similar identifier.

### Historical bug reports are test inputs, not present-tense verdicts

Firebase maintainers list iOS PWA reports involving restart, subscription state and click routing, and explicitly say they could not reproduce some reports. This is useful first-party maintenance evidence of debugging complexity; it does not establish that Firebase, a specific browser release or Tandem currently fails in those ways. [P06: Firebase known issues](https://github.com/firebase/firebase-js-sdk/wiki/Known-Issues)

WebKit bug 263687 reports cold notification taps opening the root instead of the intended URL on iOS 17.0.3. A later comment reports inability to reproduce on iOS 26.0, although the issue remains marked NEW. Preserve both observations. Test the exact release in the pilot; issue status is not a substitute for reproduction. [P07: report and later counterevidence](https://bugs.webkit.org/show_bug.cgi?id=263687)

Use a route containing sufficient stable workspace/conversation identity, retained across sign-in. Avoid relying solely on an ephemeral postMessage reaching a just-created page. Verify this architecture in the spike rather than copying timing delays from issue comments.

### PWA versus native: make the decision per participant task

| Required participant task              | PWA experiment                                                                                          | Condition that would justify a native experiment                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Receive a message and open its context | Installed web app, scoped subscription, safe fallback, correct cold tap route                           | Repeated failure on a required supported device after an isolated implementation and current platform investigation |
| Reply with a photo                     | Keyboard/camera chooser, upload progress, interruption and restart behavior                             | A named pilot's indispensable capture/sharing workflow cannot be made usable through supported web capabilities     |
| Read while disconnected                | Bounded local cache, explicit stale state, persistence/eviction handling                                | A participant needs a stronger background transfer/storage contract that the measured browser path cannot offer     |
| Answer a phone-like incoming call      | Ordinary message-style invitation plus explicit foreground acceptance, with accurately described limits | Lock-screen/system incoming-call integration is essential to the group and the web journey fails that requirement   |
| Be reachable in several workspaces     | Server push fanout for every enrolled account/device; foreground connection budget                      | Installation/account isolation or return behavior prevents the agreed multi-space journey                           |

Native calling also has obligations. Apple's PushKit callback documentation ties VoIP pushes to reporting calls through CallKit and describes termination for failing to report on iOS 13+. Android's Core-Telecom documentation requires a notification within five seconds of adding a call to the platform to obtain foreground execution priority. These are native lifecycle integrations, not features obtained by wrapping the existing webpage. [P11: Apple callback contract](https://developer.apple.com/documentation/pushkit/pkpushregistrydelegate/2875784-pushregistry), [P12: Android Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom)

An adoption decision needs a named operating owner for signing, distribution, upgrades, push credentials, dependency updates and device support. No evidence here supports an exact native-development estimate. A single thin native call prototype may answer a specific question without committing to two complete mobile clients.

## 3. Offline and low-resource participation need honest state

### Avoid two opposite storage overclaims

WebKit documents origin/overall quotas, possible eviction under storage pressure, and heuristic decisions about persistent storage requests. Its percentages are ceilings, not usable-space guarantees. Tandem should request persistence where appropriate, observe the result and handle write failure regardless of the reported quota. [P08: storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)

Conversely, it is inaccurate to claim that all installed iOS PWAs lose their data after seven days. WebKit's tracking-prevention documentation explicitly exempts Home Screen app first-party domains from that seven-day script-writeable-storage cap and describes their isolation from Safari data. That exemption does not remove the separate storage-pressure and user-deletion questions. [P09: Home Screen exception](https://webkit.org/tracking-prevention/)

Recommended cache contract for D9:

- Start opt-in per account/workspace, with an inspectable size budget and a clear “remove offline copies” action. Text-first caching should not automatically download every attachment.
- Describe “available offline through [time]” with a last-successful-sync timestamp. Distinguish never-cached, stale-but-readable and temporarily-unavailable content.
- Keep server acknowledgement, pending send, retry needed and locally saved draft visibly different. A local optimistic row does not establish durable server storage.
- Resolve logout/switch-account cleanup across message cache, drafts, pending files, thumbnails, search fragments and notifications. On a shared browser, no previous account's cached result should appear after sign-in as another account.
- When local persistence fails, preserve in-memory work where possible and say which work is at risk. Give copy/retry actions. Do not erase an unsent item to make an indicator disappear.
- A removed member's offline device cannot learn of revocation while disconnected. Enforce access on the server and clean caches on reconnect; do not promise remote recall.

### Retrying a request is a domain operation

Workbox documents browser-managed retry where Background Sync exists and a worker-start fallback elsewhere. Its default plugin handles thrown network failures, not ordinary 4xx/5xx responses. A generic queue therefore does not solve expired credentials, forbidden sends, permanent validation errors or application-specific conflict resolution. [P10: Workbox Background Sync](https://developer.chrome.com/docs/workbox/modules/workbox-background-sync)

Retain Tandem's existing request-identity and attachment-recovery work. Define the following cases before expanding background delivery:

| Interruption                                             | Required user-visible outcome                                                                                                          |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Server stores a message but acknowledgement is lost      | Retry reconciles to the same server message, preserving attribution and attachment set.                                                |
| App closes during upload                                 | On return, either resume from durably retained bytes or explicitly request the missing file; never imply a completed upload.           |
| Participant loses channel access while an item is queued | Stop automatic send, explain unavailable destination without leaking private details, and allow copying/deleting the user's own draft. |
| Account switches while a retry is pending                | Never send under the new identity, even if conversation IDs happen to collide.                                                         |
| A photo is changed while another version uploads         | Acknowledgement binds to the submitted version; UI does not attach a stale photo to a newer draft.                                     |
| Server is reachable through Wi-Fi but not cellular       | Show workspace reachability separately from general internet connectivity.                                                             |
| Cache fills during a long draft                          | Keep the draft visible, show save failure and avoid falsely marking it saved.                                                          |
| Device clock jumps                                       | Server message order and deadlines remain authoritative; local timestamps do not silently extend a call invitation.                    |

These are proposed failure-injection cases, not observed bugs. Persistent background work, readable offline history and media upload durability are three independent delivery decisions.

### A low-end phone profile must describe actual equipment

Use at least one older supported iPhone and one real Android phone representative of the pilot's lower RAM/storage tier, plus one contemporary comparison phone. Record model, RAM when known, free storage, OS/browser release, battery mode, keyboard, app installation mode and network. CPU throttling on a workstation is supplementary; it does not reproduce camera memory pressure, keyboard placement or OS process termination.

Google's Core Web Vitals guidance supplies useful shared reference targets: LCP at most 2.5 seconds, INP at most 200 ms and CLS at most 0.1, evaluated at the 75th percentile. These are not a complete messaging quality measure. A visually loaded shell can still fail to show the target conversation or acknowledge a send. [P13: measurement definitions](https://web.dev/articles/vitals)

Add app-specific observations: time to intended conversation, time to editable composer, server acknowledgement latency, bytes to open a 50-message text conversation, upload bytes per selected image, memory after repeated conversation changes, and recovered versus lost pending work. Record foreground reconnect separately from cold launch. Avoid collecting message content to measure those times.

Proposed constrained profile for comparison: 1.6 Mbit/s down, 750 kbit/s up, 300 ms added RTT; a second run adds 2% loss and a 30-second outage. These numbers define a reproducible experiment, not a claim about India or any other region's typical network. Use a physical network interruption or a proxy covering worker traffic; Workbox specifically warns that Chrome DevTools' page offline checkbox does not necessarily block service-worker requests. [P10](https://developer.chrome.com/docs/workbox/modules/workbox-background-sync)

## 4. Accessible reading is a dynamic behavior, not a label count

WCAG 2.2 supplies specific criteria to map to journeys: 1.4.4 text resizing, 1.4.10 reflow, 2.1.1 keyboard access, 2.4.11 focus not obscured, 2.5.8 minimum target size, 3.3.8 accessible authentication and 4.1.3 status messages. The minimum target criterion uses 24 by 24 CSS pixels or stated exceptions; it is not an unconditional rule that every control must be 44 pixels. Test 200% text resizing and reflow at a 320 CSS-pixel equivalent width, subject to the criterion's exceptions. These checks alone cannot support a whole-product conformance claim. [P14: WCAG 2.2](https://www.w3.org/TR/WCAG22/)

The WAI-ARIA `log` role fits ordered, appended updates and has polite live-region semantics. An indefinitely paged, edited and trimmed message history needs more care than applying `role="log"` to the entire container. [P16: ARIA log semantics](https://www.w3.org/TR/wai-aria-1.2/#log)

The APG feed pattern illustrates an explicit relationship between reading focus, scrolling and dynamic loading. It also acknowledges the lack of an established keyboard convention for feeds. Treat it as a design reference rather than a mandate to recast chat as a feed. A simpler, explicitly paged reading mode may prove more usable. [P15: APG feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/)

Proposed conversation-reading experiment:

1. Place focus on a message in older history. Receive five new messages, insert older messages above it and change one reaction count. The reader should retain both message identity and access to its controls.
2. Offer a concise new-message announcement/indicator without repeatedly reading the whole transcript. Let participants choose whether new message text is spoken. Typing indicators must not crowd out content.
3. Open a thread or message action, close it, and return to the initiating message. When that message is deleted or trimmed, move to a predictable nearby context with an explanation.
4. Load older history through an explicit keyboard/screen-reader action; do not require the virtual reading cursor to trigger a visual scroll threshold.
5. Reach the composer, history and navigation without hundreds of Tab presses. Keep shortcut help discoverable and do not commandeer common assistive-technology key combinations without testing.
6. On a phone, open the keyboard, rotate and show a permission/error banner. The active field, current candidate and send/error controls remain reachable and do not disappear behind fixed overlays.

Test at least NVDA with a selected Windows browser, VoiceOver with Safari on an actual iPhone, and TalkBack with Chrome on Android, plus keyboard-only and zoom/reflow sessions. Record exact versions and the participant's usual settings. An automated scanner cannot establish whether new replies are intelligible or whether someone can return to the message they were reading.

Voice notes broaden participation only if listeners can also use them. Retain the earlier community study's caution about language-specific transcription. For the first voice-note pilot, offer typed context, replay/seek and visible duration, and measure whether recipients can retrieve the important detail. Do not label automatic captions an accessibility solution until target-language accuracy, latency and correction behavior have been evaluated.

## 5. Multilingual composition is broader than translating buttons

### Preserve language input and recipient selection

UI Events specifies composition events and `KeyboardEvent.isComposing`; its publication status is a specification draft, not proof that every keyboard/browser sequence is identical. Tandem already has a composition guard. Preserve it and test actual Japanese/Chinese/Korean candidate confirmation, mobile dictation, Indic input, paste, undo and switching input methods while a draft is open. [P17: UI Events](https://www.w3.org/TR/uievents/)

A more concrete current-source question is mention discovery. With the inspected ASCII mention-query parser, a participant may be unable to narrow autocomplete by typing a non-Latin display name after `@`, despite those names being considered by candidate filtering. Validate a person with an Arabic, Devanagari and Japanese display name; show stable recipient identity when selecting a suggestion. A generic ASCII handle fallback does not automatically make discovery easy for a group using another script.

### Preserve displayed text and identity

W3C internationalization guidance distinguishes page direction from direction of inserted text, and describes `dir="auto"` and `bdi` for content whose direction is unknown. Apply the distinction to names, mixed-language messages, filenames, code, numbers and times. Mirroring the entire UI is insufficient; content direction must not reorder adjacent identity/status text misleadingly. [P18: direction guidance](https://www.w3.org/International/questions/qa-html-dir)

Unicode segmentation defines extended grapheme clusters for user-perceived character boundaries and notes that word boundaries can require language-specific tailoring. Composer's current UTF-16 length can differ from the number of visible characters. Keep protocol byte/code-unit limits explicit where required, but use grapheme-aware display/truncation and explain the limit accurately. Do not cut an emoji sequence or combining mark in a notification/name merely to fit an arbitrary character count. [P19: Unicode text segmentation](https://www.unicode.org/reports/tr29/)

Unicode's security mechanisms address confusable identifiers and mixed-script restrictions; they do not justify banning non-Latin display names or all mixed-language text. Preserve expressive names while showing an unambiguous handle/account and workspace when accepting a contact, assigning a role or opening an invite. Treat visual-confusability checks as a risk signal whose false positives need review. [P20: Unicode security mechanisms](https://www.unicode.org/reports/tr39/)

Suggested fixture set for human-reviewed trials: a Japanese name entered by IME; Devanagari text with combining marks; Arabic text containing an English filename and a time; a family emoji; composed/decomposed accented names; a long display name; and two visually similar display names owned by different accounts. Verify send, edit, copy, quote, notification preview, invite preview and member selection. Root-level research covers full-text-search language behavior separately; successful composition does not establish search parity.

Translation readiness should also include plural forms, incomplete translations, date/number formats and time zones. An event needs an unambiguous absolute time and local rendering, including daylight-saving transitions where relevant. Do not infer location or personal identity from the chosen language. A two-language validation is a useful engineering gate, not evidence that all languages are supported.

## 6. Contact controls must survive alternate routes

### Separate the promises

Use distinct concepts: **mute** controls interruption, **hide** controls local presentation, **block contact** refuses specified personal interactions, **leave** changes membership, and **report** shares selected evidence with authorized reviewers. Each action should explain its effect on shared spaces. A block cannot remove copies another person already obtained.

Signal's documentation is a useful counterexample to an overly simple “blocking means invisibility” claim. It describes asymmetric shared-group visibility, confusion caused by hidden messages, and no replay of blocked messages when unblocked. Tandem should choose and describe its own behavior rather than copy a button with unstated semantics. [P21: Signal block behavior](https://support.signal.org/hc/en-us/articles/360007060072-Block-numbers-usernames-or-groups)

W3C's Privacy Principles emphasize minimizing personal data and respecting contextual identity. They are design principles, not a legal certification. For Tandem, joining a workspace should not implicitly grant discoverability across other workspaces, unrestricted personal calls or notification previews on shared devices. [P22: W3C Privacy Principles](https://www.w3.org/TR/privacy-principles/)

### Resolve these cases in the contact-policy prototype

| Route or ambiguity                                    | Recommended policy question / failure to prevent                                                                                                                                                                                              |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pending DM request                                    | What exact preview is shown before acceptance? A request must not trigger remote-media downloads, external link previews, typing/read signals or call invitations by default. Rate-limit repeated requests and explain recipient controls.    |
| Existing conversation exception                       | Creating a DM row must not forever bypass a later restrictive policy. Define when contact was accepted, how acceptance is revoked and what happens to queued messages.                                                                        |
| Group DM containing a blocked or disallowed recipient | Do not silently create a smaller group and immediately send the authored message. Show the final recipient set and require an explicit send decision; use neutral refusal wording that does not disclose the recipient's private block state. |
| Shared channel mentions/reactions                     | Suppress personal interruption consistently across push, Activity, badges, email/bridges if later present, reply previews and call invitations. Decide whether the content is folded or shown.                                                |
| Block then unblock                                    | Decide whether past requests/messages remain rejected; prevent automatic replay floods. Preserve the blocker’s own access to relevant history and reporting controls.                                                                         |
| Person changes handle or display name                 | Bind blocks to immutable account identity; display updates must not erase the relationship. A new account is a separate abuse-control problem.                                                                                                |
| Administrator or integration messages                 | Any policy exception must be explicit and narrowly scoped. A bot quoting a blocked person's content is not automatically safe. Avoid a silent “admin can always DM” override.                                                                 |
| Caller cancellation and quiet hours                   | An immediately cancelled call should not automatically become a noisy missed-call item. Coalesce repetition, separate audit history from attention and allow the recipient to suppress call attempts.                                         |
| Multiple devices / stale client                       | Server authorization decides the outcome. A restored outbox, notification action or old client must not bypass a block applied elsewhere.                                                                                                     |
| Report evidence                                       | Preview what messages/attachments and identity will be shared, who can review it, and whether the reported host/admin is among them. Avoid automatically attaching a whole private conversation.                                              |

These are proposed design choices to validate; they are not represented as competitor features or completed Tandem safeguards.

### Calls expose more than a ringtone

The WebRTC standard explains that establishing communication can expose proposed IP addresses to the other party, and describes limiting that exposure through relay-only policy. A muted microphone is not a promise that network identity or room presence is hidden. [P24: WebRTC privacy considerations](https://www.w3.org/TR/webrtc/#privacy-and-security-considerations)

RFC 8828 discusses different IP-handling modes and their privacy/connectivity tradeoffs, including proxy behavior. Browser configuration and network conditions affect the result. Do not claim that mDNS host-candidate masking makes all peer addresses private, or that entering TURN credentials alone forces relaying. [P25: WebRTC IP handling](https://www.rfc-editor.org/rfc/rfc8828.html)

Consequently, a blanket rule allowing a blocked participant to join any shared-channel huddle needs explicit review. Alternatives include a clearly explained shared-room exception with presence preview, stronger room admission, or a relay-only mode for untrusted-contact calls. A block applied during a call also needs defined teardown/continuation behavior. Measure relay capacity and cost before promising the stronger mode. Peer-address exposure, participant visibility and moderator access are different decisions.

### Account control and support are part of trust

A USENIX study conducted five focus groups with 17 IPV professionals and four with 11 customer-support practitioners. It recommends trauma-informed support and cautions against promises to solve participants' problems. Its qualitative setting does not estimate the prevalence of abuse in Tandem or validate any proposed block policy. [P23: Zou and colleagues, 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/zou)

Design implications, to validate with appropriate expertise: make session review and revocation understandable, separate the participant's needs from the workspace operator's, and let people inspect the consequences of reporting or changing credentials before acting. A host may be part of the problem; “ask your administrator” is not always a complete support path. Do not promise that one click makes an unsafe household or device safe. Research recruitment should not require survivors to disclose private histories merely to test ordinary controls; start with synthetic scenarios and expert review.

Push confidentiality also needs precise language. RFC 8291 encrypts the payload between the application server and user agent through a push service. That protects a transport segment; it is not participant-to-participant message E2EE against the workspace host. [P05: Web Push encryption](https://www.rfc-editor.org/rfc/rfc8291)

Before enrolling a device, show preview choices such as generic notification, sender-only, or message text, with a sample. Explain the host, any Tandem-operated relay and browser/OS push provider in plain language. Subscription cleanup after sign-out, account removal and device revocation belongs in the same slice as subscription creation. Minimize information in URLs, fallback notifications and diagnostic exports.

Recipient-set changes require visible review. Test reports with a host-as-subject scenario. Unsettled shared-room policy blocks public-community/call claims.                                                                                                                             |
| **P-G9 Phone responsiveness — D2**           | At least 30 comparable runs per selected device/network profile; a small history and a media-heavy history; camera/keyboard/rotation plus 50 conversation changes.                                                                                                 | Publish p50/p75/p95 task times, data transfer and termination counts. Proposed constrained-profile target: intended text conversation editable within 5 seconds at p75, with no crash or lost draft. Investigate regression above 20% versus the recorded baseline; adjust targets from pilot need before promising them.                                                                   |
| **P-G10 Native decision — D7/D8**            | Document one indispensable failed PWA task, a minimal reproduction on required platform versions, attempted fixes and a native spike of the same task.                                                                                                             | Commit only if native materially resolves the blocker and has a maintenance owner. If only background calling fails, do not infer that all messaging requires a rewrite.                                                                                                                                                                                                                    |

For P-G2, 30 events are an engineering smoke sample, not evidence for high-reliability percentages; repeat over several days and varied real use before publishing availability claims. Record platform-suppressed events separately from app defects. Do not silently remove failed observations after changing implementation; retain before/after evidence.

## 8. What would change the recommendation

- **Phone installation is the dominant abandonment point:** test guided installation and whether a native distribution path materially improves completion before investing in richer messaging.
- **Groups mainly need reliable photos and short messages:** prioritize D1/D2 and media durability; direct-call infrastructure can remain conditional.
- **An essential lock-screen calling journey fails:** fund a narrow native call prototype with its lifecycle and relay costs, without assuming a browser wrapper solves it.
- **Offline history is rarely used but drafts fail:** fix work preservation first; do not introduce a large sensitive cache merely for a “local-first” label.
- **Assistive users lose context under live updates:** favor an explicit reading mode/paging design over further timeline virtualization until the reading contract is validated.
- **Requests/blocks are not understood:** simplify visible choices and explain shared-space effects; more hidden exceptions will increase the mismatch.
- **The pilot needs stronger confidentiality from the host:** revisit E2EE as a separate architecture and recovery project. Self-hosting and Web Push payload encryption do not establish that property.

Remaining unknowns: actual target-device distribution, required OS support horizon, install willingness, browser/OS update practices, background delivery in the eventual deployment, minimum viable bandwidth, acceptable cache footprint, representative assistive setups, target languages, translation ownership, and the groups' tolerance for shared-room contact exceptions. None can be filled in by more competitor feature counting. The next evidence should be an observed, consented group journey using the concrete gates above.

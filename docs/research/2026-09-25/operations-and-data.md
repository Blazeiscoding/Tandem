# Tandem operations and data: recovery, trust boundaries and realistic capacity

Research and read-only source inspection: **September 25, 2026**. This extends the [earlier operations memo](../2026-09-24/operations-research.md), [product research](../../PRODUCT-RESEARCH-2026-09-25.md) and [roadmap](../../PRODUCT-ROADMAP-2026-09-24.md). The proposed [hosting registry](../../HOSTING-REGISTRY-2026-09.md) and [state tables](../../STATE-TABLES-2026-09.md) were read as design context; their proposals are not implemented behavior. No product code changed, no tests or builds ran, and no existing workspace database was opened. Two runtime-version queries used disposable in-memory databases.

**The main new conclusion is that restoring a valid archive can still recreate an unsafe or misleading service.** A backup can pass every checksum while reviving revoked credentials, starting queued integrations twice, rolling a client back behind work it already acknowledged, or creating two reachable servers with the same workspace identity. The next release should make replacement, rehearsal and rollback explicit operations. This is a stronger near-term investment than clustering or an expanded administration console.

Sources O25–O48 continue the earlier operations sequence O01–O24. All were accessed **2026-09-25**. Official documentation establishes documented behavior, not Tandem reliability or demand. Recommendations, formulas and acceptance thresholds below are proposed engineering judgments. No WAN call measurements, power-loss tests, fresh-machine recovery, packaged-update run or security penetration test was performed.

## 2. Backup consistency is a contract over database, blobs and configuration

SQLite's current `VACUUM INTO` documentation says the output is a consistent database snapshot; interrupted generation may leave an incomplete file. It also says completed output is flushed when the source connection's synchronous setting is NORMAL or FULL. Older claims that this command never flushes output would be inaccurate against the current page. It purges deleted database content from the generated copy, while the incremental backup API trades that compaction for less CPU and incremental operation. [O26: VACUUM](https://sqlite.org/lang_vacuum.html), [O27: Online Backup API](https://www.sqlite.org/backup.html)

Tandem's database snapshot precedes attachment copying. Its documented response to a concurrently deleted referenced blob is to fail verification, not silently certify an incomplete backup. That is a sensible existing failure policy. A stopped-server capture remains the simplest first supported guarantee. For live scheduled backups, choose and document one of two approaches after measuring downtime tolerance:

1. Briefly suspend writes and physical blob deletion, capture the database plus a retained blob inventory, then release normal work once the required files cannot disappear. Copying can continue after the short suspension if retention is guaranteed.
2. Keep immutable blobs and defer garbage collection for the lifetime of a backup lease. Capture a database snapshot, copy exactly its inventory, then release the lease. Handle expired leases after crashes.

These are proposed designs, not claims that either lease exists today. New uploads after the snapshot belong to the next backup. A failed attempt should remain visibly incomplete and never advance “last successful backup.” Keep the previous good backup until the new one is verified and safely stored.

Separate three success statements: **verified bytes**, **durably completed destination**, and **restored usable workspace**. Hashes/integrity checks address the first. Audit filesystem flush and rename behavior for blobs, manifest and destination directory before promising survival of immediate power loss. Actual storage controllers and network destinations also matter. SQLite documents corruption hazards from broken filesystem locking, particularly on network filesystems. Recommend local supported storage for the live database and transfer completed backups to remote destinations. A cloud-synchronized live folder is not a supported multi-host database architecture merely because it contains a `.db` file. [O29: SQLite corruption hazards](https://www.sqlite.org/howtocorrupt.html)

The proposed backup inventory should distinguish:

| Inventory class       | Include or reference                                                                                     | Restore decision                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Workspace history     | Database, referenced attachments, manifest, format/schema/build identifiers                              | Verify before any replacement.                                                                                              |
| Deployment behavior   | Public address, retention settings, file limits, invitation defaults, trusted proxy policy, RTC settings | Show included values and omissions; avoid silently adopting permissive defaults.                                            |
| External dependencies | Domain/tunnel provider, connector version, token-file location, backup destination, relay service        | Explain which require reauthorization on the new host.                                                                      |
| Secrets               | Database signing keys; optionally separately encrypted deployment secrets                                | Declare sensitivity and recovery-key requirements. Do not label an archive “safe to share” because login tokens are hashed. |
| Host-local state      | Registry entry and data path; optional installation notes                                                | Rebuild paths for the destination rather than transplanting absolute paths.                                                 |
| Client-local state    | Saved sign-ins, unsent drafts and downloaded copies                                                      | Explicitly outside a server-only backup unless a separate client export exists.                                             |

Estimate free space by the actual path: source, snapshot, copied blobs, staging copy, existing destination and retained superseded directory can overlap in time. A universal “twice the database size” check misses attachment-heavy workspaces and same-volume staging. Show required and available bytes per destination volume, with an operational reserve for writes during capture.

### A runtime inventory finding, with reassuring local counterevidence

SQLite's WAL documentation describes a rare race affecting older engines with concurrent connections writing/checkpointing. It identifies fixes in **3.51.3**, with backports **3.44.6** and **3.50.7**, and cautions against interpreting its rarity as a routine emergency. WAL also permits only one writer at a time, ordinarily uses same-host shared memory and can accumulate a large log when long readers prevent checkpoint completion. SQLite documents an exception that avoids shared memory when exclusive locking guarantees a single process; it does not establish safe multi-host writes. [O25: WAL and WAL-reset fix](https://www.sqlite.org/wal.html)

Read-only local checks found:

| Runtime actually queried                            | Embedded Node | SQLite from `SELECT sqlite_version()` |
| --------------------------------------------------- | ------------- | ------------------------------------- |
| Installed standalone Node                           | 24.16.0       | 3.53.0                                |
| Locally installed Electron 44.1.0, run in Node mode | 24.19.0       | 3.53.3                                |

Both local engines are beyond the stated fix. The standalone engine reported `DEFAULT_SYNCHRONOUS=2`. These observations are **not** an inventory of shipped installers, user machines or future builds. Add Electron/Node/SQLite versions and effective `journal_mode`/`synchronous` values to release evidence. `node >=24` and an Electron semver range alone cannot establish which database engine a package contains. Do not change durability settings to chase throughput without measuring the acknowledged-write loss window.

## 3. Restore, rollback and deletion need separate policies

Offer **rehearse recovery**, **replace the live workspace**, and eventually **create an independent copy** as different flows. An independent copy should remain deferred until IDs, credentials, authorship and external integrations have explicit semantics; changing only its display name is insufficient.

For a rehearsal, validate and inspect history while preventing public/LAN publication, scheduled sending, outgoing integration traffic and future push dispatch. Also prevent destructive housekeeping from changing the inspected snapshot before validation. Isolation should be enforced before server initialization, not by a UI checkbox applied after timers start. Loopback binding alone is insufficient: outbound jobs can still reach external services. Use a dedicated recovery startup policy plus network containment in the drill.

For replacement, keep logical workspace identity stable, revoke the old deployment's ability to serve or send, restore to a fresh destination, review identity/session policy, switch reachability, validate from a participant device, then enable scheduled/outbound work deliberately. A startup instance ID is useful for health routing; it is not a durable replacement authorization or an anti-rollback generation.

Consider a **recovery generation** that changes after an intentional history rollback, separately from the stable workspace ID. Clients can then explain “This workspace was restored” and reconcile cached sequence state, pending actions and already-observed messages. This is a hypothesis to prototype; it does not by itself stop two uncoordinated hosts from claiming to be current. The first release can require the old process and tunnel credentials to be disabled, rather than introduce a distributed lease service.

| Restored state                                | Why it can surprise people                                                      | Required policy before resuming                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Login sessions revoked after the backup       | The old backup may still contain an unexpired valid hash.                       | Default to invalidating restored sessions, with a documented recovery-admin route and an explicit continuity alternative only if justified. |
| Bot/webhook tokens rotated after the backup   | Old secrets retained by a third party may match restored hashes again.          | Review/rotate integration credentials before making the restored service reachable.                                                         |
| External HMAC signing secret                  | A test clone can sign requests as the original service.                         | Suppress all external deliveries during rehearsal; rotate or explicitly approve the production secret on replacement.                       |
| Scheduled messages and delivery queue         | External effects after the snapshot are absent from restored completion state.  | Display due work and choose hold/reconcile/resume; retain event IDs for receiver deduplication.                                             |
| Deleted messages/files or deactivated members | Historical state may reappear.                                                  | State the rollback date and review access/retention before publication.                                                                     |
| Post-backup uploads                           | A database-only rollback may refer to blobs that were physically deleted later. | Restore a matching full backup; check every referenced attachment before traffic returns.                                                   |
| Client outbox                                 | A retry can target a service whose history moved backward.                      | Preserve existing nonce/identity safeguards and test same-ID rollback explicitly.                                                           |

These are source-derived rollback hazards, not reproduced incidents. Existing [integration delivery](../../INTEGRATIONS.md) is explicitly at least once and asks receivers to deduplicate by event ID. A restore must preserve that contract; a local “sent” transaction cannot guarantee exactly-once behavior at a remote receiver across rollback.

**Database-only pre-upgrade copies have a bounded role.** They help reverse migration failures while the corresponding attachments remain available. Once a new release accepts writes, retention runs or file deletion proceeds, “install the previous binary and copy back the database” may lose accepted work and break file references. For the initial release process, define an upgrade maintenance window, capture a full recovery set, perform migration, verify before opening writes, and treat a rollback after writes reopen as a declared history rollback with loss/reconciliation choices.

Retention should describe both live visibility and historical copies. A deleted message can remain in older backups, superseded restore folders, client downloads and external integration systems. `VACUUM INTO` cleaning the new database snapshot does not erase those copies. Proposed product wording should name the live retention period, backup retention period, who can restore history and whether restored data is screened before republishing. Avoid promising remote erasure of files already downloaded.

Litestream is a credible later option for reducing the database recovery window, but its documentation describes asynchronous replication and warns against multiple producers writing the same replica location. Its normal database-replication path does not define a Tandem database-plus-attachment recovery point. Adding a replication process introduces checkpoint, replication-lag, credential and restore ownership to operate. Retain complete verified workspace backups even if incremental database replication is piloted. [O28: Litestream caveats](https://litestream.io/tips/)

## 4. Availability, identity and confidentiality are different promises

Cloudflare tunnel replicas add connector ingress paths to an origin; the documented routing is not application-state replication or a guarantee of a particular replica. Running two `cloudflared` instances on the same sleeping laptop cannot keep the underlying workspace alive. Routing one hostname to two independent restored SQLite workspaces would create divergent service state. Keep a single authoritative application writer until there is an explicit replication design. [O30: Tunnel availability](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/)

The health display should answer four understandable questions: is the local service running; does the public address reach this running instance; can a signed-in participant read/write; do notifications and calls work on this device/network? Diagnostics can reveal more detail on demand. An external probe from another network is needed before marking Internet access ready. The host's own successful fetch can conceal split DNS, an inaccessible ingress route or local-only success.

The supported stable-host recipe should name the owner of DNS/tunnel credentials, restart behavior, sleep/power expectations, connector updates and backup recovery. A second human must be able to obtain the recovery instructions when the original host is unavailable. That does not require enterprise identity management.

A public HTTP tunnel carries the application transport; it is not automatically a public WebRTC relay. Cloudflare documents additional client requirements for its non-HTTP published services. Test media on its own reachable TURN/SFU endpoints rather than infer support from a working chat URL. [O31: Published application protocols](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/protocols/)

Publish a small trust-boundary explanation:

| Party                | What the first supported architecture should disclose                                                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace host/admin | Can access server-held history and database signing material; host-controlled storage is not message E2EE.                                                              |
| HTTPS reverse proxy  | May terminate participant TLS before forwarding to the origin. Encryption on both legs is different from excluding the proxy from plaintext access.                     |
| Push service         | Standards-based payload encryption can protect content from the forwarding service; transport metadata and delivery dependency remain.                                  |
| TURN provider        | Relays media traffic; charges and network exposure depend on the path. A full participant media-confidentiality claim needs a separate signaling/endpoint threat model. |
| Bot operator         | Receives content allowed by app permissions and may retain copies outside workspace retention.                                                                          |
| Backup recipient     | Can recover history and embedded secrets unless the backup is appropriately encrypted and keys protected.                                                               |

Cloudflare's Full (strict) documentation shows separate visitor-to-Cloudflare and Cloudflare-to-origin encrypted connections and origin certificate verification. It is useful evidence for explaining TLS boundaries, not a universal instruction for Tunnel's distinct connector configuration. [O32: Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)

## 5. Push feasibility should measure delivery, privacy and operating work

WebKit's published path supports Web Push for Home Screen web apps after a user-initiated permission request, without Apple Developer Program membership. That makes a PWA feasibility slice reasonable; it does not establish reliable delivery on Tandem's supported phones, installation flows or power policies. [O33: WebKit announcement](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

RFC 8291 specifies content confidentiality/integrity between the application server and user agent through an intermediary. It does not hide messages from the application server producing the encrypted payload. Therefore “encrypted push content” is a supportable design aim while “end-to-end encrypted conversations” would be a different claim. Keep subscription credentials out of diagnostic bundles and protect registration with authenticated HTTPS. [O34: Web Push encryption](https://www.rfc-editor.org/rfc/rfc8291)

RFC 8030 allows expiration of messages/subscriptions and distinguishes acceptance from delivery mechanisms. Do not turn a provider's accepted response into “the person was notified.” Track enqueue, provider acceptance/rejection, optional supported receipts, and actual app opening separately. Expired subscriptions should stop repeated retries; transient failures need bounded backoff. On reconnect the message history is authoritative even if every notification was lost. [O35: HTTP Web Push](https://www.rfc-editor.org/rfc/rfc8030)

Proposed first contract: one device subscription per installation/account/workspace; privacy-controlled preview text; a short-lived route identifier; preference and membership checks at dispatch; pruning on permanent rejection; idempotent event/device scheduling. Decide what happens when a message is deleted or access revoked after a notification is queued. The tap must recheck authorization rather than trust content in the notification.

A basic demand worksheet is `notifications = qualifying events × eligible recipients × subscribed devices`, adjusted for batching and retries. One mention can reach several installations. Record actual endpoint counts, payload bytes, queue age, acceptance failures and operator work. Provider fees may be zero for a tested path while engineering, always-on hosting and support costs remain. Do not import Rocket.Chat/Zulip service quotas into an unrelated Web Push design, and do not infer background call ringing from message delivery.

## 6. Calls need a capacity model, temporary credentials and measurable recovery

Tandem's [huddle implementation](../../../packages/client-core/src/huddle.ts) creates one peer connection per remote participant, with microphone, camera and screen tracks. This makes a mesh bandwidth model directly relevant. For `n` participants each transmitting `b` Mbit/s to every other participant, a simplified model is:

- Per-participant upload: `(n − 1) × b` Mbit/s.
- Aggregate directed payload traffic: `n × (n − 1) × b` Mbit/s.
- One hour of that aggregate: `0.45 × n × (n − 1) × b` decimal GB.

Illustrative arithmetic, **not measured Tandem performance**:

| Simultaneous participants | Upload each at b = 1 Mbit/s | Aggregate payload GB/hour | At b = 0.05 Mbit/s, aggregate GB/hour |
| ------------------------- | --------------------------- | ------------------------- | ------------------------------------- |
| 2                         | 1 Mbit/s                    | 0.90                      | 0.045                                 |
| 4                         | 3 Mbit/s                    | 5.40                      | 0.270                                 |
| 6                         | 5 Mbit/s                    | 13.50                     | 0.675                                 |
| 8                         | 7 Mbit/s                    | 25.20                     | 1.260                                 |

The model excludes packet overhead, retransmission, silence behavior, adaptive encoding, separate screen traffic and changes in sender count. It does not assert actual codecs, stream bitrate or browser encoder count. Partial relay use changes billed traffic. Two-relay paths and provider definitions can change accounting further; measure rather than applying one universal multiplier.

Cloudflare currently documents TURN at **$0.05/GB outbound from its edge to TURN clients**, a **1,000 GB free tier** and exceptions for traffic to its own Realtime SFU/Stream. At that unit rate, a hypothetical 5.4 GB fully billable hour would be $0.27 before allowances. This is an example of a provider's meter, not a Tandem price quote or a recommendation to select it; taxes, account terms and future changes require a fresh check. [O38: TURN billing FAQ](https://developers.cloudflare.com/realtime/turn/faq/)

`/api/rtc-config` currently returns configured ICE servers to authenticated users. If those settings contain reusable TURN credentials, distributing them is necessary for clients to connect, but their reuse and rotation need a policy. Coturn documents time-bound credentials generated using a server-held shared secret. Prototype per-user/time-limited issuance; keep the signing secret on the server, rate-limit issuance and test long-call refresh/ICE restart. Expiring authorization must not strand legitimate calls unexpectedly. [O37: Coturn authorization](https://github.com/coturn/coturn/blob/master/README.turnserver)

Measure selected candidate type, bytes sent/received, round-trip time, loss/jitter and reconnect outcomes through available WebRTC statistics. Browser support varies; redact raw candidate IPs/SDP and avoid recording call content in support bundles. [O36: WebRTC statistics specification](https://www.w3.org/TR/webrtc-stats/)

Run 2/4/6/8-person experiments across direct UDP, relayed UDP and restrictive-network TCP/TLS paths, with actual phones and a sustained screen share. Include a participant joining late, Wi-Fi/mobile handoff, revoked microphone permission, device unplug and a signaling reconnect. Capture CPU, battery and uplink conditions along with call outcomes. A TURN allocation test is not proof of sustained two-way audio.

An SFU is conditional: introduce one if measured participant uplink/CPU or required room size fails the pilot's promise. It reduces repeated client uplink copies but adds a media service, deployment topology and a new trust/operating boundary. LiveKit's documentation separates signaling, ICE UDP/TCP and TURN/TLS ports, showing why adding an SFU still requires a network design. It is not a drop-in remedy supplied by the chat HTTPS tunnel. [O39: LiveKit ports and firewall](https://docs.livekit.io/transport/self-hosting/ports-firewall/)

## 7. Distribution security includes the updater, native bridge and saved credentials

Electron's security guidance covers current framework versions, sandboxing/context isolation, permissions, constrained navigation and validation of IPC senders. Tandem already implements several of these controls. Review every hosting/storage IPC handler and preload method against the same trust boundary; some inspected handlers validate senders explicitly while others do not in their handler body. That difference identifies an audit target, not a demonstrated bypass. Server-provided message content and attachment names remain untrusted even when loaded inside a locally packaged renderer. [O40: Electron security](https://www.electronjs.org/docs/latest/tutorial/security)

For release provenance, retain the source commit, lockfile, build-tool/runtime versions, dependency inventory, build logs, artifact hashes, signatures and compatible recovery artifact. A repeatable build process is not automatically a proven bit-for-bit reproducible build. GitHub's attestations can link a binary to source/workflow identity, but must be verified and do not certify that the resulting code is secure. Use them as provenance evidence, not a substitute for a signed and tested installer. [O43: Artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)

Electron documents signing for distribution and macOS signing plus notarization. The first supported platform should have a rehearsed install/update/uninstall/data-preservation path before adding more support promises. Signing credentials are external release prerequisites, not a reason to claim unsigned artifacts have been authenticated. [O41: Code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)

Use version-appropriate updater documentation. The repository declares electron-builder **26.x**, so this memo used its v26 documentation: NSIS is supported; macOS auto-update requires signing, and the updater's macOS path also needs ZIP metadata/artifacts alongside DMG. The checked-in Tandem config declares only a DMG target for macOS and does not itself establish a working automatic updater. Plan feed ownership, supported source/target versions, signature verification, staged rollout, interrupted downloads and schema compatibility before C10. [O42: electron-builder v26 updater](https://www.electron.build/v26/docs/features/auto-update/)

Signing protects artifact authenticity; it does not choose the correct workspace shutdown or migration moment. A desktop host update should stop new work, complete/bound outstanding operations, verify recovery material, stop the server, apply the package, migrate and verify, then reopen public traffic. A failed update should leave intelligible recovery instructions even when the normal UI cannot launch.

OS-protected client secrets are also platform-specific. Electron describes Windows DPAPI as protection against other OS users, not other programs running as the same user; Linux secret-store availability varies. Tandem already refuses the weak Linux backend. A new host may need sign-in and tunnel reauthorization rather than a promise that copying encrypted settings preserves usable credentials. Test signature changes against macOS Keychain behavior as platform support expands. [O48: safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

## 8. Bot scope should follow one useful recipe

Tandem's [integration contract](../../INTEGRATIONS.md) explicitly has no OAuth installation flow or scopes: a bot token can invoke every supported method within its reachable conversations, and posting to public channels does not require membership. That is a meaningful permission boundary to improve before encouraging broadly installed third-party apps. Incoming webhooks already fix their destination channel and can be a narrower first integration path.

Slack separates `chat:write.public` from normal writing, and its history method combines relevant history scopes with bot membership. These are useful examples of action and resource permissions being distinct; they do not imply Tandem should reproduce Slack's full scope catalogue or OAuth ecosystem. [O44: Public posting scope](https://docs.slack.dev/reference/scopes/chat.write.public/), [O45: History permissions](https://docs.slack.dev/reference/methods/conversations.history/)

Start with one pilot-required CI/monitoring/RSS recipe and a small proposed permission set:

| Recipe need                          | Proposed explicit permission                                                  |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| Announce build outcomes              | Post to named channel(s); no history access.                                  |
| Reply when directly invoked          | Receive invocation plus bounded context in channels where installed.          |
| Answer from conversation history     | Read named conversations; disclose that history leaves the workspace.         |
| Post without joining public channels | Separate elevated choice; absent by default.                                  |
| Follow all workspace events          | Separate choice from message content and from specific channel subscriptions. |

Show a permission preview in ordinary language. Adding history access or new channels should require an administrator to see the changed grant. Define removal, token rotation and app deactivation separately; Slack's `auth.revoke` illustrates that revoking a bot token can deactivate the bot/remove memberships without uninstalling the app. Tandem can choose different semantics but must make them explicit. [O46: Token revocation](https://docs.slack.dev/reference/methods/auth.revoke/)

Preserve outbound destination validation, bounded response sizes, deadlines, signature checks and retry deduplication. OWASP recommends controlling destinations and redirect behavior to prevent server-side request forgery. Tandem already has relevant defenses and a deliberate private-hook opt-in; future previews, fetchers and adapters should reuse that boundary instead of creating a second unguarded request path. A LAN bot is legitimate, so an explicit narrow destination allowance may be a better later design than disabling all private-network checks globally. [O47: OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

## 9. Practical acceptance and failure matrix

These are proposed release experiments. Thresholds should be agreed for a stated pilot/device/workload before running them; no row below is claimed to have passed in this research.

| Scenario                                         | Required observable result                                                                                           | Failure means                                                  |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Backup while a referenced attachment is deleted  | Complete inventory or explicit failed attempt; earlier verified backup remains available.                            | Never display a fresh successful backup for a partial capture. |
| Destination fills during database/blob copy      | Clear failure; no live-workspace mutation; staging identified for cleanup.                                           | Capacity preflight/reserve or failure handling is inadequate.  |
| Fresh-machine rehearsal                          | Counts, memberships, selected old/new files, scheduled state and settings inventory match; zero external deliveries. | History ownership gate C2 is not met.                          |
| Old and restored hosts both start                | Rehearsal cannot publish; replacement procedure exposes/fences the old deployment before cutover.                    | Stable ID alone is being mistaken for service authority.       |
| Restore after logout/token rotation              | The chosen credential policy is enforced and explained; revoked access is not accidentally re-enabled.               | Recovery security policy is incomplete.                        |
| Restore predates sent integration event          | Queue is held/reconciled; same event ID survives where applicable; receiver dedup behavior documented.               | Exactly-once assumptions exceed the implemented contract.      |
| Upgrade fails during migration                   | Matching old runtime and recovery set can restore the declared point; no unsupported downgrade opens the new schema. | C5 rollback promise is unproven.                               |
| Rollback after new uploads/deletions             | Explicit accepted-work loss boundary and consistent restored blobs.                                                  | Database-only rollback is unsafe for that case.                |
| Sleep/reboot/tunnel disconnect                   | Participant sees accurate unavailability; host restart and public-identity probes recover.                           | “Always available” cannot be promised for that recipe.         |
| Domain or tunnel change                          | No unnoticed switch to unrelated workspace; old links/installations have an explicit recovery path.                  | Reachability and logical identity are improperly coupled.      |
| Locked-phone permission refusal/expiry           | Useful diagnostics, bounded retry and recovery without lost message history.                                         | Phone-led pilot gate D1 fails even if foreground chat works.   |
| Two-way media under forced relay/network handoff | Sustained audio, measured transport path, visible recovery or clear failure.                                         | Calls capacity promise must narrow or architecture change.     |
| TURN credentials expire during long call         | Refresh/reconnect behavior meets the declared call contract; old credentials cannot be reused indefinitely.          | Authorization lifetime and media lifecycle disagree.           |
| Update artifact tampered/interrupted             | Invalid artifact refused; previous working installation/data remain recoverable.                                     | Automatic delivery must not ship.                              |
| Bot removed while delivery waits                 | Content access and queued sends follow the declared removal policy across all paths.                                 | Scope enforcement is incomplete.                               |
| Restore deleted/expired history                  | Operator sees affected historical state before exposure; current retention is explicitly applied or reviewed.        | Deletion and recovery statements are misleading.               |

## 10. Stage the architecture around proven needs

| Stage                             | Concrete scope                                                                                                                                               | Evidence before advancing                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| First durable private pilot       | One authoritative SQLite host; stable HTTPS recipe; registry adoption; guided full backup; isolated recovery; manual signed release where credentials exist. | A second person restores on a fresh destination, participants return, no unintended external work occurs.      |
| Dependable daily use              | Scheduled verified off-device backups, bounded push, small-call diagnostics, runtime inventory, required bot recipe with explicit permissions.               | Locked-device trials, sustained measured calls, useful backup failure notices and repeatable upgrade recovery. |
| Demand-driven expansion           | Incremental database replication, larger-room SFU, broader platforms, richer import/export or scoped app installation.                                       | Measured recovery-window, uplink/CPU, distribution or integration demand exceeds the first architecture.       |
| Conditional organization features | HA/failover coordination, federation, E2EE or enterprise identity lifecycle.                                                                                 | A named adoption need plus a funded design for their identity, recovery and compatibility consequences.        |

The next research session should prioritize observed failures over adding more sources: one representative fresh-machine restoration, one same-ID rollback reconciliation experiment, one phone delivery matrix and one WAN media baseline. This memo supplies hypotheses and acceptance criteria for those trials; it cannot replace them.

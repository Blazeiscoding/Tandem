### REV-01 — Contain every background queue entry

**Evidence:** [server.ts:4033](../packages/server/src/server.ts) reads due schedules outside the per-item catch; immediate/timer callers at 4077 and 4088 call it directly. Event-delivery flushing at 725 has no outer rejection handler, and publication/timer callers at 606 and 4092 discard its promise. The hourly `maintain` wrapper already exists, but does not cover these paths. [Actual native callback probes](research/2026-10-02-deep/server-report.md#server-01--native-background-entry-failures) now show process exit 1 through the scheduled interval, scheduled continuation and delivery interval. SQLite stays consistent; the continuation retains the unsent durable schedule. No physical disk fault was reproduced.

**Implementation:** add shared containment for synchronous and asynchronous background operations, record bounded failure/retry metadata, and preserve durable work after failure. Apply it to startup, timer and immediate continuations. Keep explicit operational callers able to learn that work failed. Ensure one failed queue does not skip another and failed startup releases acquired resources.

**Acceptance:** a real child-process server survives injected queue read/write failures through the actual timers, continues serving chat, keeps queued sends/events, resumes after repair, and stops cleanly. Assert no unhandled exception/rejection, no event publication from failed transactions and no overlapping drain jobs. Convert the research process-failure probes into survival regressions; add write-failure/backlog cases, which are not established by the current read-failure reproduction.

### REV-02 — Make file cleanup fair and promptly drain healthy backlog

**Evidence:** [store.ts:1558](../packages/server/src/store.ts) returns an unordered `LIMIT 100`. [server.ts:909](../packages/server/src/server.ts) leaves failed paths in the queue, so repeated flushes can select the same blocked page. Routine cleanup runs every 15 seconds. The [extended real-filesystem reproduction](research/2026-10-02-deep/server-report.md#server-02--cleanup-starvation-persistence-and-accounting) survives restart with 101 pending entries and the healthy file retained; repairing the failing paths plus two turns clears all entries. Storage accounting is correct and must be preserved.

**Implementation:** persist retry eligibility/attempts, use stable ordering, back off individual failures, and continue healthy backlog on bounded later turns. Expose pending/failed cleanup counts and age. Keep storage bytes reserved until deletion succeeds; resume safely after interruption. Invalid entries need an explicit visible disposition, not endless immediate retries.

**Acceptance:** 100 failing entries cannot block a healthy 101st deletion; thousands of healthy files drain without waiting 15 seconds per page or blocking chat. Restart retains retry state. Permanent failures stay visible, deleted content is never reattached, and accounting follows successful deletion.

### REV-13 — Deliver precompressed hashed assets with useful caching

**Evidence:** [real direct-server HTTP measurements](research/2026-10-02-deep/root-http-assets.json) show entry JS/CSS served without compression and with `max-age=0` at [server.ts:1166](../packages/server/src/server.ts). **Implementation:** generate `.br`/`.gz` alongside built web assets and enable supported static precompressed delivery. The [plugin's maintained precompressed-delivery documentation](https://github.com/fastify/fastify-static#precompressed) describes the supported option.

**Acceptance:** real standalone and desktop-host HTTP negotiates all three encodings with identical decoded content and correct MIME/headers; repeat navigation reuses hashed assets and a new build refreshes HTML/chunk references. HTML/private attachments are never made immutable. Missing chunks return useful failures while valid SPA routes work. Fresh container artifact retains compressed files when Docker is available. Measure first usable conversation under a declared bandwidth/cache condition before making latency claims.

**Evidence:** [native auxiliary-window controls](research/2026-10-02-deep/desktop-report.md#2-p1-boundary-hardening-authorize-each-sensitive-ipc-sender) read a synthetic saved token and persist settings through a hidden `about:blank` window with the real preload. Guarded file download rejects the same sender. At-rest encryption works; a child iframe has no direct bridge. Creating the auxiliary window requires native harness privileges; ordinary app navigation/window-open controls prevent the demonstrated setup. No remote exploit or cross-origin credential access is established.

**Implementation:** register sensitive storage/hosting handlers through one boundary that checks the authorized live WebContents, actual sender frame and trusted renderer URL. Add explicit authorized windows if multi-window operation is intended. Apply payload schemas/limits and a narrow credential/storage contract without weakening acknowledged-storage semantics. [Electron's security guidance](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages) recommends validating IPC senders.

**Acceptance:** foreign-window sensitive read/write/hosting calls fail before work; legitimate commands and GL-01–03 storage acknowledgements pass. Exercise direct foreign/child-frame calls under the selected policy and document normal same-origin parent delegation. A sender guard does not promise protection against arbitrary code already running in the trusted renderer.

### REV-15 — Keep retries within admission limits and free healthy endpoints

**Evidence:** [real queue probes](research/2026-10-02-deep/server-report.md) show authenticated retry restores 1,000 failed rows into an already-full 500 waiting queue, leaving 1,500 waiting. Separately, a held response blocks another endpoint's next event through the global `Promise.all` barrier, though its first event succeeds and server health stays 200. The production outbound deadline bounds this delay; indefinite starvation is not established.

**Implementation, slice A:** define ready/failed-history row and byte budgets. Promote a bounded ordered retry prefix or a separate durable retry backlog; expose retried/remaining counts and preserve work. Apply capacity consistently to repair and ordinary admission.

**Implementation, slice B:** prototype a bounded pump that refills freed slots while allowing at most one in-flight event per subscription. Preserve per-subscription order, redaction, eligibility, deadlines, shutdown abort and total concurrency. Add aggregate limits only against a declared integration envelope.

**Acceptance:** repeated fail/retry cycles never exceed the ready-work ceiling, retain remaining retry work and drain after repair. With an unrelated response held, the healthy endpoint's next ordered event starts without waiting for the held batch. Verify bounded resources, restart/revocation/shutdown and compare mixed chat/integration latency before accepting the new pump.

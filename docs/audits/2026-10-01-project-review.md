**Six additional reproduced findings**

1. **P2 — A live message can disappear while the final newer-history page loads.** In [workspace.ts](../../packages/client-core/src/workspace.ts), lines 787–789 deliberately skip live appends while a timeline is anchored. `loadNewer`, lines 1381–1401, does not hold those arrivals and clears `hasMoreNewer` based on its earlier response. A real authenticated server/socket probe captured the final page, received another live message, then delivered that page: the new message was absent and `hasMoreNewer` was false. Both newer-history controls disappear; reopening loaded history can reuse the incomplete state. Buffer/reconcile arrivals before declaring the window the live tail, while preserving continuity across gaps. This is a display/sync defect; the server retained the message.

2. **P2 — A history response can overwrite an edit already received live.** [workspace.ts](../../packages/client-core/src/workspace.ts), lines 1268–1297 and 1359, holds newly created messages but does not replay edits over captured history. Real-server probes held initial-history and message-jump responses, edited a contained message, waited for the reader socket to process the update, then released each response. The UI showed the old words while the server retained the edited words. Give history responses a snapshot sequence and replay later relevant events, as thread loading already does. Apply the rule consistently to initial/latest, around, older and newer pages; include reaction/pin/deletion races in the regression cases.

3. **P2 — Losing access to an unrelated channel strands a thread in loading state.** [workspace.ts](../../packages/client-core/src/workspace.ts), line 691, increments the global history epoch when removing one channel. An in-flight thread response for another accessible channel then fails `current()` at line 1446 and returns at line 1453 without clearing its loading state. Actual API/socket reproduction: hold a `general` thread response, leave a different private channel, release the response; `general` remains accessible, but the thread stays `loading=true`, `loaded=false`. Scope invalidation to the removed channel's tickets and thread IDs, or explicitly settle/restart affected requests.

4. **P2 — Editing a mention does not refresh connected readers' badges.** [server.ts](../../packages/server/src/server.ts), lines 577–586, publishes mention-count changes for creation and deletion only. The edit updates the database and mention index, but [workspace.ts](../../packages/client-core/src/workspace.ts), line 845, only patches message content. Actual HTTP/socket reproduction: plain text → mention returned 200, authoritative count became 1, but the reader remained at `{}`. Removing a mention changed authoritative count 2 → 1 while the reader stayed at 2; both edits emitted zero count frames. Refresh readers affected by both the old and new text after the committed edit.

5. **P2 — Huddle join/leave bypasses the ephemeral rate limit.** [gateway.ts](../../packages/server/src/gateway.ts), lines 256–260, accepts transitions without `affordEphemeral`, unlike typing and signalling. Alternating transitions fan participant updates out across a public workspace. With an ephemeral burst/rate of one, an actual socket received all 40 join/leave updates, while ten typing attempts correctly produced one update. Bound/coalesce transitions per account; ensure a real departure and disconnect cleanup can still complete. This requires an authenticated account; no unauthenticated exploit is claimed.

6. **P2 — Repeated failed scheduled backups accumulate partial database copies.** [backup.ts](../../packages/server/src/backup.ts), lines 159–185, creates output and writes the database before attachment-copy failures, with no failure cleanup. [hosting.ts](../../apps/desktop/src/main/hosting.ts), line 903, chooses a fresh directory on retry; lines 1210–1217 leave failures due and prune only after success. Pruning at line 1127 skips directories without manifests. An actual workspace/controller/settings probe with a missing referenced blob ran three due passes with `keep: 1`: three incomplete directories remained, each with a 393,216-byte database and no manifest, totaling 1,179,648 bytes. Desktop checks due backups every 15 minutes. Capture into uniquely owned staging, clean it on failure, publish after verification, and bound/back off retries. Preserve pre-existing user-selected directories. Persistent failures can fill the backup destination; no actual full-disk event was induced.

**Further improvements**

- **Protect message edits from stale devices.** A fresh authenticated HTTP probe changed a message from device B, then submitted device A's stale replacement. Both returned 200; A overwrote B. The UI warns only after it has observed a live change. [editMessageBody](../../packages/protocol/src/rest.ts), line 222, accepts text without a revision precondition, and [server.ts](../../packages/server/src/server.ts), line 1807, applies unconditional replacement. Add a baseline revision/text check and a conflict response while retaining explicit overwrite. An extra `expectedText` field in the probe was discarded by the current schema; the existing client does not send it. This is an already-recognized product contract gap, now exercised again.
- **Make backup/retention health durable and visible.** Show the last verified backup, last failure and retry state across restarts; provide interrupted-restore recovery and off-device restore drills. Add shutdown/worker deadlines and cancellation. Managed Cloudflare connectors need ongoing route verification; external carriers already poll. These operational recommendations have not all been reproduced as outages.
- **Broaden admission controls and privileged IPC validation.** Huddle transitions have a demonstrated bypass above. Other mutations, aggregate sockets and temporary capabilities need explicit capacity policies; validate privileged IPC senders/frames. Current renderer isolation/navigation restrictions are present, and no remote IPC exploit was demonstrated.
- **Cover the actual packaged dependency graph in desktop CI.** [desktop.yml](../../.github/workflows/desktop.yml) includes selected shared UI paths, but many components/styles and web packaging resources can change without triggering packaged checks. Expand filters or select affected packages from dependency relationships. Keep a dependable executing CI/release gate; this review does not assert the current remote account/billing state.
- **Split large modules along existing domain boundaries.** Server routing/lifecycle, client history/preferences/outbox, hosting backup/public-link control, and HostDialog contain multiple independent state machines. Extract them incrementally after regression coverage for these races; preserve transaction/event ordering. A broad rewrite is unnecessary to address these defects.
- **Target the missing tests.** Add success-reordering, initial absent-key races, fresh-input save failure, maintenance broadcasts, membership changes during unrelated requests, and cleanup after each acquired resource. Existing tests cover many ordinary and older-failure paths, but the green suite misses these specific interleavings.

The full dependency audit found esbuild 0.27.7 through tsup and Vitest/@vitest/mocker 3.2.7. The upstream advisories describe a Windows esbuild development-server file-read issue, patched at 0.28.1, and exposed mocker/plugin file-read paths, patched in Vitest 4.1.11. Plan compatible build/test tool upgrades; this review demonstrated no shipped exploit path. See the primary [esbuild advisory](https://github.com/evanw/esbuild/security/advisories/GHSA-g7r4-m6w7-qqqr) and [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9).

**Suggested execution order**

1. Atomic initialization and per-conversation draft persistence; durable fresh-send acceptance.
2. Reliable shutdown/restore cleanup, integrity-screened upgrade retention, and failed-backup staging cleanup.
3. Timeline response/event reconciliation and channel-scoped invalidation.
4. Mention refresh on edits/retention and explicit unread precedence.
5. Shared retry lifetime, serialized settings/toggles, huddle admission, toolchain/CI and operational evidence.

## Source-supported risks to verify in a browser or load test

**S7 / P1: authenticated file bytes may bypass later authorization through the browser HTTP cache.** At the inspected snapshot, `server.ts:1770-1827` rechecked session and channel access before opening the file, then replied to ordinary authenticated GETs with `Cache-Control: private, max-age=31536000, immutable` at line 1824. “Private” permits a browser cache to store and reuse a fresh response; it does not make that cache account-specific ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7)). The URL was stable across accounts and there was no `Vary: Authorization`. Inference: after Alice loaded a private attachment, a later same-browser request for that URL by Bob or after Alice's access was revoked could be satisfied locally without the server's fresh access check. Ticket downloads correctly used `no-store`; `FileCache` already provided a bounded in-memory preview cache. The proposed fix was `no-store` for bearer-authenticated file responses and a real-browser cross-account/revocation regression. PR #115 later reproduced the cache reuse in Chromium and verified the fix returns 404 after access loss.

**S8 / P1: scheduled work has no admission cap or bounded drain.** `server.ts:3262-3317` accepts schedules without a rate/quantity limit. `store.ts:1824-1830` returns every outstanding item to the user; `store.ts:1841-1851` returns _all_ due and held rows; `server.ts:3624-3662` processes them synchronously every 15 seconds. Held rows are revisited and rewritten on every round. A member can accumulate a large queue of 12 KiB texts and cause repeated full scans, synchronous writes, and a long event-loop stall when they become due. Bound queue admission per account/workspace, page due work into small batches, and give held rows a `next_attempt_at` rather than retrying every tick. Keep restart recovery and idempotent completion. Load-test a large held queue and a 50,000-message workspace while the desktop window remains responsive. This is a code-path risk; the actual stall threshold needs measurement.

**S9 / P2: restored data still carries live side effects.** This is mostly handled: `backup.ts` verifies checksums, database integrity, foreign keys and file inventory; restore stages a checked copy and keeps the superseded directory. `isolated` blocks schedules, outbound app calls, and mDNS. The remaining operational risk is starting the same restored data without `isolated`: valid sessions, waiting schedules, and app deliveries resume by design. `inventoryBackup()` and CLI text call that out. The app's restore flow should display that inventory and default inspection copies to isolated mode; a fresh-machine drill should verify the old and new instances cannot both deliver under the same identity.

## Verified strengths and deliberate gaps

- Session expiry/deactivation is checked on REST and socket fanout; gateway sends access changes after membership commits. The event log and most message mutations are transaction-backed.
- Outbound HTTP rejected private addresses by default, validated the address in the socket lookup, limited response bytes, and did not follow redirects. The missing wall-clock deadline was closed by PR #115.
- Event subscriptions have durable retries, per-subscription ordering, a 500-pending ceiling, failed-backlog controls, and membership-revocation cleanup. This is current code, so older roadmap claims about missing retries are stale.
- Attachments had streaming quota accounting, orphan cleanup, one-shot download tickets, and backup inventory verification. Scheduled-file reservation remains open; PR #115 closed the ordinary GET cache-policy gap.
- `Gateway` models huddle participation as `channelId -> Set<userId>` (`gateway.ts:37-41,291-323`). Two devices of one account share one seat and signals fan to every socket for that user; device-level participation and reconnect handling are product gaps already identified in `docs/REMAINING-WORK-2026-09.md`, not a newly found regression.
- Channel creation and app configuration are currently governed by fixed role rules. Workspace-configurable policy is a roadmap gap, not a defect in the current contract. The server/Store monolith and lack of a route-drain deadline are also tracked engineering work; splitting files should follow behavior fixes and regression tests.

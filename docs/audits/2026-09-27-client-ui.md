## Reassess the baseline before assigning work

The September 24 audit's generic navigation, touch and accessibility gaps are now stale. `route.ts` represents channel, thread, panel, dialog and a channel reading anchor; `WorkspaceScreen` writes and consumes those routes; the web end-to-end test exercises Back, Forward and reload. Messages have a persistent touch action menu; a shared roving hook makes a message list one Tab stop; quick switcher suggestions have combobox/listbox semantics; the DND decision precedes notification delivery; profile and DM failures have visible messages. See `packages/ui/src/lib/route.ts`, `packages/ui/src/components/MessageItem.tsx:375`, `packages/ui/src/lib/useRovingMessages.ts:12`, `packages/ui/src/components/QuickSwitcher.tsx:117`, `packages/client-core/src/notify.ts:54`, and `tests/e2e/web.spec.ts:1789`. Plan against these specific implementations rather than reopening the older umbrella tickets.

The strongest remaining issues are state contract failures. A thread can mark unseen channel content read; outbox retention silently drops older pending work; restart retries text sends that the server already refused; scheduled replies ignore an adjacent delivery choice. These are concrete source findings, not feature wishes.

## Confirmed findings

### CU-1 — Opening a thread can clear unread channel messages and mentions (P1)

`ThreadPanel.readVisibleReplies()` calls both `client.markRead(channelId, max(root.seq, all loaded reply seqs))` and `client.markThreadRead(rootId)` (`packages/ui/src/components/ThreadPanel.tsx:54-70`). The former advances the **channel's global** cursor (`packages/client-core/src/workspace.ts:1879`; `packages/server/src/store.ts:703-710`). Activity unread and unread mention counts both select messages with `m.seq > cm.last_read_seq` (`packages/server/src/store.ts:2767,2803`). Thus reading one thread also acknowledges intervening top-level channel messages, other threads and their mentions, even when the main timeline is inactive behind a panel (`packages/ui/src/screens/WorkspaceScreen.tsx:877,910`).

Deterministic acceptance case: a channel has a thread root at seq 10, an unread top-level mention to the viewer at seq 11, and a reply in that thread at seq 12. Put the channel cursor at 10. Open the thread from the Threads list on a narrow viewport and read its latest reply. The thread's read cursor may advance to 12; the channel cursor must remain at 10, the seq 11 message must remain in Activity and the mention badge must remain. Repeat from a different active channel, after Back/Forward and after reconnect. A correction needs a clear decision about whether thread replies contribute to channel unread counts; merely removing `markRead` can leave those counts surprising. Define separate conversation and thread acknowledgement semantics, then test server query, client state and UI together. The existing `unread.test.ts` checks `markThreadUnread` without touching the channel, but does not exercise `ThreadPanel`'s read path.

### CU-2 — The 51st pending send silently removes an older item from restart recovery (P1)

`WorkspaceClient.send()` accepts and appends pending items without a bound (`packages/client-core/src/workspace.ts:1425-1469`). `outboxSnapshot()` serializes only `.slice(-OUTBOX_LIMIT)` and `OUTBOX_LIMIT` is 50 (`packages/client-core/src/workspace.ts:75,1541-1553`). `DraftPersistence` persists that snapshot (`packages/ui/src/components/DraftPersistence.tsx:70-112`), while the composer clears its draft as soon as `client.send()` returns (`packages/ui/src/components/Composer.tsx:345-361`). If 51 text sends are pending or have failed during an outage, the oldest is present only in memory and vanishes on restart, without a limit notice. A busy offline participant can cross this bound without typing unusually long messages.

Acceptance case: make 50 queued text sends unavailable to the server, attempt the 51st, reload, and account for every message the composer said it accepted. Either durably preserve every accepted item within a documented storage budget, or reject further enqueue **before** clearing the composer and explain the limit. Include separate cases for one local storage write failure, a browser tab close, and a desktop restart. The send API should report enqueue acceptance to the composer; a successful in-memory append alone does not prove persistence.

### CU-3 — Restart automatically retries a terminally refused text send (P1)

`StoredPending` carries nonce/body/attachments but no delivery classification (`packages/client-core/src/workspace.ts:63-73`). The live client maps `channel_archived`, `channel_not_found`, `bad_thread_root`, `nonce_conflict` and deactivation to explicit failure reasons (`packages/client-core/src/workspace.ts:81-106`). Yet `outboxSnapshot()` discards `failed` and the refusal reason, and `restoreOutbox()` sets `failed` only when attachments are present, then calls `deliver()` for every text-only entry (`packages/client-core/src/workspace.ts:1541-1586`). The existing live UI asks the author to press Retry (`packages/ui/src/components/MessageTimeline.tsx:600+`); a restart changes that choice to automatic retry. For example, a message refused because a channel was archived may be sent without another action if it was reopened before the restart.

Acceptance case: queue a text send while a channel is archived, observe the archived refusal, reopen it, restart the app, and verify that the message remains a failed outbox item until the author chooses Retry. Separately, a network timeout with an uncertain acknowledgement should reconcile automatically using the same nonce and never duplicate the server message. Persist a typed delivery state and distinguish uncertain transport outcomes from known server refusals. Include revoked membership, deleted thread root and a request the server accepted before its response was lost. `recovery.test.ts:184-216` covers network retry and lost acknowledgement, not known refusal across a restart.

### CU-4 — “Also send to channel” is ignored by Send later (P2)

The thread composer displays the `Also send to channel` checkbox and `Send later` together (`packages/ui/src/components/Composer.tsx:815-863`). Immediate send passes `alsoSendToChannel: alsoToChannel` (`Composer.tsx:345-354`). `schedule()` constructs a body without that choice (`Composer.tsx:408-418`); the scheduled request schema has no field for it (`packages/protocol/src/rest.ts:110-121`), and the scheduled route persists no broadcast flag (`packages/server/src/server.ts:3262-3312`). A scheduled reply selected to appear in the channel will only appear inside the thread. The server's ordinary send route does support broadcasting (`server.ts:1618`), so the mismatch is specific to scheduling.

Acceptance case: choose the checkbox, schedule a reply and let the scheduler deliver it. Confirm it appears both in the thread and main channel timeline, with a durable flag included in request identity, storage and delivery. If scheduled broadcasting is deferred, make the incompatible choice unavailable with an explanation before accepting the scheduling request. Check restart recovery of the exact scheduled payload and that a retry cannot change its target visibility.

### CU-5 — Non-Latin display names cannot narrow mention suggestions (P2)

The suggestion filter does compare display names (`packages/ui/src/components/Composer.tsx:283-295`), but `refreshMentionState` recognizes only ASCII letters, digits, dot, underscore and hyphen after `@` (`Composer.tsx:318-326`). Typing `@山`, `@न`, or `@ع` clears the mention query. Since suggestions are capped at six, a participant in a larger workspace may be unable to choose a person by the name they see. The IME Enter guard is already present (`Composer.tsx:514-515`); preserve it while extending discovery.

Acceptance case: with at least eight users, put Japanese, Devanagari and Arabic display-name targets beyond the first six default results. Type each name after `@` using normal keyboard/IME input; each target must appear and selection must insert the correct ID token. Include a combining mark, paste, Backspace, an ASCII handle and `@channel` as regression fixtures. Test on the composer and a real mobile input method; a code-unit regex test alone cannot establish the interaction.

## Attention, retrieval and participation contracts requiring an explicit decision

These paths are concrete, but the present product contract does not say which outcome is intended. Treat them as design-and-test tickets rather than declaring a regression from source alone.

- **Replayed notifications.** `WorkspaceClient` labels an event `live:false` when it predates the connection snapshot (`packages/client-core/src/workspace.ts:511,748`). `WorkspaceScreen` suppresses only the screen-reader announcement for those events (`packages/ui/src/screens/WorkspaceScreen.tsx:640-647`). It still calls `decideNotification` and `platform.notify` (`WorkspaceScreen.tsx:650-659`). In `notify.ts:58-65`, replayed DMs, direct mentions, `@channel` and every-message channels can each create an OS notification; only `@here` is quiet when stale. After a long outage this can fan out one interruption per historical event. Specify which missed events should interrupt once, enter Activity only, or be batched, with deduplication across reconnects. Test an outage containing 100 messages, mixed reasons, an already-read item and a second reconnect. Avoid simply dropping missed obligations without a catch-up path.
- **Active-channel suppression hides unopened threads.** With page focus, any message whose `channelId` equals `activeChannelId` returns before notification policy runs (`WorkspaceScreen.tsx:650`). A reply in an unopened thread is therefore silent even when its thread is followed; the main timeline does not show it unless broadcast. Define the followed-thread alert and feed contract, then test active channel with another thread open, a modal open, a scrolled-back timeline and a covered phone panel. This is coupled to CU-1's read model.
- **Thread reply retrieval loses its exact place on route transitions.** A jump to a reply holds `targetId` only in panel state (`WorkspaceScreen.tsx:595`); the route serializes the root ID (`WorkspaceScreen.tsx:400,439`; `route.ts:47-57`). `ThreadPanel` centers the target on first load (`ThreadPanel.tsx:112-125`) but stores no thread reading anchor. Back/Forward or reload can reopen the thread at its latest replies rather than the selected reply. Existing end-to-end route coverage proves that a thread and its draft reopen, not exact reply position in a long thread (`tests/e2e/web.spec.ts:1898-1930`). Decide whether exact reply URLs remain one-time navigation or a restorable place; test a reply older than the first fetched page in a long thread, after a side-panel visit and reload.
- **Failed media actions offer no explanation.** Camera and screen share controls catch every error without a visible state (`packages/ui/src/components/HuddleControls.tsx:16-31`), and peer audio playback rejection is discarded (`packages/ui/src/components/HuddleBar.tsx:16-27`). Device permission refusal, unavailable hardware and playback policy therefore look like an inert control. Calls also use default capture devices (`packages/client-core/src/huddle.ts:98-115,400+`) and leave the huddle on socket close (`workspace.ts:439-441`) without a rejoin state. Define actionable permission/device/network states before claiming dependable calls. Exercise camera denial, screen picker cancellation, device unplug, autoplay refusal, socket loss and sleep/wake on supported browsers.
- **Closed-app phone delivery is absent.** The web platform constructs `new Notification` from the running page (`packages/ui/src/platform.ts:201-211`); `apps/web` has no manifest or service worker registration in the inspected source. The installed/closed/locked delivery claim needs a stable HTTPS origin, push model, privacy and device matrix from the 25–26 September research. Do not infer it from the existing permission banner or desktop notification test.
- **Personal contact controls are still a policy gap.** `ProfileDialog` offers Friends and Message (`packages/ui/src/components/ProfileDialog.tsx:66-92`), and Friends are workspace-local (`FriendsDialog.tsx:103-105`). The inspected UI has no block/report flow. Define server-enforced behavior for DM creation, existing group DMs, mentions, shared-channel content, huddle invitation/join, search and notification previews before adding a profile button. Validate both sides of a relationship and an already-open client. This is a cross-layer ticket, not a UI-only edit.
- **Search presents only message results.** `SearchDialog` shows newest-first messages and an attachment count, with no filename result or ordering control (`packages/ui/src/components/SearchDialog.tsx:296-424`). The server's FTS and language probe are covered by the separate retrieval research. Preserve membership checks when adding filenames/files and carry the selected result's context through navigation. Evaluate known-answer tasks before changing default sort.
- **Phone and screen-reader validation remains empirical.** The source has a touch menu, a 760px phone sheet, a 1023px panel overlay, focus trapping, a roving message list and a bounded live announcement. Existing Playwright coverage uses Chromium and emulated touch; it cannot establish VoiceOver/TalkBack behavior, software keyboard placement, safe-area handling or background delivery. Use real devices with named OS/browser versions and 200% text/reflow plus older-message paging tasks. The stylesheet has no `env(safe-area-inset-*)` or `visualViewport` handling in the inspected client; test before deciding whether the current padding fails on target phones.

## Implementation sequence for Codex or Claude

1. **Stabilize the state contracts (CU-1–CU-3).** Start with a truth table for channel versus thread read cursors and outbox `in-flight / uncertain / known-refused / missing-files / accepted` states. Record what is durable and what the UI can honestly say. Use API and store fixtures before changing panels. Then implement CU-1 and outbox state/retention together with integration tests. A shared `markRead` cursor is the dependency for Activity and notification work; a recoverable outbox is the dependency for background sending.
2. **Close the scheduled-delivery mismatch (CU-4).** Make the checkbox's meaning stable across immediate, scheduled and recovered sends. Change protocol, durable schedule schema, request hash and scheduler atomically; provide compatibility behavior for older clients/servers. This is a bounded slice after the send state semantics are explicit.
3. **Restore exact thread return.** CU-5's parser and code-level composition/paste cases merged in PR #116. Design thread route/anchor restoration with a long-history fixture so a fix does not overwrite an intentional channel reading position; verify the mention behavior on an actual mobile input method in the participation gate.
4. **Specify attention policy using event scenarios.** Resolve replay batching, active-channel unopened threads, followed-thread feed/notification effects and DND/read interactions in one table. Implement that policy across `notify.ts`, `WorkspaceScreen` and server counts. Build deterministic reconnect tests and a focused two-device E2E scenario; stop using the presence of an OS notification as proof the recipient saw it.
5. **Run the participation gate for the intended cohort.** Real phone foreground/background/reload, NVDA/VoiceOver/TalkBack, IME, camera/microphone denial, network switch and sleep/wake. Keep a dated device/OS/browser matrix with observed failures. The outcomes determine whether push, offline cache, native mobile or call infrastructure is the next investment.

For each slice, the agent implementing it should update or supersede the older roadmap line it closes, and attach one reproduction that failed before the change plus one regression scenario around access/restart. Do not treat the passing test totals below as coverage for the newly identified transitions.

# Gatherline improvement plan

Reviewed September 6, 2026, against `6aaf4fd` and the current working tree.

The recommended direction is to make Gatherline dependable enough for a small team to use every day, make hosting understandable to a non-specialist, and then expand its capabilities. Keep the shared web/desktop UI, simple SQLite deployment, local hosting, and compatibility with existing workspace data.

This is an assessment and implementation plan. Priorities below distinguish reproduced failures, gaps found in code, and proposed features. A passing existing suite is the baseline, not proof that all user journeys work. The assessment was written before any source changed; **Implementation progress** below records what has since been built against it.

What was still open on September 15, item by item, and the order to do it in, is in [REMAINING-WORK-2026-09.md](REMAINING-WORK-2026-09.md).

### Existing strengths to retain

- Shared typed protocol and shared React UI across browser and desktop.
- Real integration tests, browser tests with media assertions, and a packaged desktop smoke-test workflow.
- SQLite WAL storage, versioned migrations, full-text search, and a straightforward data directory.
- Streamed server uploads/downloads, a 300-message window per timeline, and idle attachment-cache eviction.
- Bounded password-hashing concurrency, hashed session tokens, checked incoming socket frames, and a slow-socket buffer limit.
- Private-channel checks, protected owner/admin roles, signed integration requests, and DNS-time checks for outbound destinations.
- Working threads, mentions, reactions, drafts, pins, saved items, scheduled sends, friendships, and small mesh huddles. Improve their completeness rather than counting them as missing features.

## Delivery sequence

P0 blocks a dependable release. P1 belongs in the next usable release. P2 is valuable after the foundations are stable. P3 is conditional expansion.

Effort is a planning aid: **S** is usually one focused PR, **M** several related PRs, **L** a milestone spanning multiple subsystems, and **XL** a separate design/validation project. These are relative sizes, not delivery-date commitments.

| Milestone                          | Outcome                                                              | Main work                           | Dependencies / exit gate                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 0. Reliable core                   | Messages, access changes, retries, and shutdown behave correctly     | R01–R08, essential regression tests | Reproduced failures become passing permanent regression tests; faults do not create partial message/event state. |
| 1. Protected accounts and data     | A host can safely claim, recover, and preserve a workspace           | A01–A06, O01, O02                   | Safe first-run claim, real sign-out, account-separated local data, verified backup/restore, bounded abuse.       |
| 2. Complete daily chat             | Writing, reading, finding, and following conversations feel coherent | U01–U08, C01–C08                    | Browser/desktop feature parity; keyboard and narrow-window journeys; no silent failure of important actions.     |
| 3. Comfortable collaboration       | Calls and shared information work beyond happy paths                 | H01–H05, C09–C11                    | Device/error handling and real-network call validation; stable threads, search, and file workflows.              |
| 4. Easy operation and integrations | A non-developer can run a workspace and diagnose problems            | O03–O08, I01–I05                    | Upgrade/restore drill, host controls, usable diagnostics, reliable integration deliveries.                       |
| 5. Release and capacity            | Supported packages and realistic operating limits are established    | E01–E08                             | CI actually exercised, release artifacts verified, soak/capacity results published with workload and hardware.   |
| 6. Selective expansion             | Larger deployments get capabilities justified by demand              | X01–X07                             | Separate requirement and architecture decisions; retain a simple small-workspace deployment.                     |

Engineering modularity, focused tests, and accessibility work start during milestone 0 and accompany each feature. They are not cleanup postponed until milestone 5.

## R — Correctness and synchronization

| ID  | Priority / effort | Planned work and acceptance criteria                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R01 | P0 / M            | **Repair reconnect and resync.** Separate the snapshot high-water mark from the last applied event; define when replay is complete. Do not assume globally consecutive sequence values because private events are filtered. Preserve local drafts/outbox during snapshot replacement, reconcile lost access, handle server rollback/cursor reset, and explicitly handle incompatible protocol versions. Verify offline creates, edits, deletes, reactions, threads, and pins against loaded caches, including replay overflow and repeated reconnects. |
| R02 | P0 / M            | **Make sends idempotent.** Persist a uniqueness rule scoped to the authenticated sender and stable request key; define mismatched-key reuse behavior. Retries reuse the same key and uploaded file references. HTTP success and WebSocket delivery use the same reconciliation function, in either order. Lost response, repeated retry, and reconnect produce one message, one attachment binding, and one event.                                                                                                                                     |
| R03 | P0 / L            | **Introduce transactional mutation services.** Validate inputs and permissions before writes; commit entity changes and durable events together; publish only after commit. Cover registration/invite consumption, channel/member creation, messages, app creation/deletion, and scheduling. Treat filesystem cleanup and outbound HTTP as post-commit work with retry/compensation. Inject failures between steps and prove no partial state is visible or persisted.                                                                                 |
| R04 | P0 / M            | **Tie sockets and huddles to valid access.** Track session identity, close that session's sockets on logout, revoke all sessions on account-wide actions, and remove revoked users from signalling rooms. Send an explicit personal access-change event even when the former channel audience excludes the leaving user. Purge affected client channel/thread/file state. Test multiple devices and private-channel departure during an active call. Previously downloaded content cannot be retroactively erased from another person's machine.       |
| R05 | P1 / M            | **Complete membership synchronization.** Send authorized channel metadata when someone gains access; remove/invalidate it when access ends. Keep preferences, member lists, active navigation, and huddle rosters consistent. Existing private-channel invitations appear immediately without a reload.                                                                                                                                                                                                                                                |
| R06 | P1 / M            | **Make scheduled delivery recoverable.** Validate roots and attachments both when queuing and delivering. Use queued/held/failed/sent states with atomic completion, bounded retry, failure reasons, and a defined policy for deactivation/reactivation. A missing root, archived channel, or changed membership cannot silently lose or misplace the message.                                                                                                                                                                                         |
| R07 | P1 / S–M          | **Make shutdown deterministic.** Stop accepting work, stop timers, drain/cancel in-flight tasks, finish socket close callbacks, then close the database. Make repeated stop calls safe. Exercise huddles, unauthenticated sockets, uploads, and scheduled work during shutdown and failed startup.                                                                                                                                                                                                                                                     |
| R08 | P1 / M            | **Unify request validation and asynchronous state rules.** Apply positive bounded pagination schemas to every history/search/list route; validate IDs, channel names, membership arrays, file references, and action payloads. Add request deadlines, cancellation, stale-response protection, and in-flight deduplication where reads can overlap. Malformed input yields a useful 4xx; switching channels cannot apply an obsolete response over newer state.                                                                                        |

### Follow-up review of the combined changes

- **Backup completeness and restore integrity (O01):** metadata and row counts now come from the copied database. Only attachments referenced by that snapshot are copied; a missing or wrong-sized blob fails capture. Verification validates manifest fields and attachment paths, cross-checks the database's actual schema, counts, foreign keys and file inventory, and rejects overlapping backup/workspace directories. Restore copies files without loading whole blobs into memory and verifies the staged copy before moving existing data. Concurrent deletion can still prevent capture; stop the server for a predictable complete backup. Nine added regressions cover missing inventory, unsafe paths, a misleading schema declaration, overlap and writes during capture.
- **Session and credential access (A01/R04):** the added session-list/revocation, password-change, admin-reset and ownership-transfer APIs now have dedicated account tests. Expiry is checked before incoming socket actions and outgoing durable, broadcast and personal traffic, as well as on heartbeat. Receiving traffic does not extend expiry. Login and password changes recheck credentials/session validity after asynchronous hashing; admin reset rechecks current roles before committing. Password updates and session revocation share a database transaction.
- **Owner setup (A02/U03):** forwarded requests require the startup claim code. The browser now displays that field, submits it, and preserves registration input when a code is rejected. The full browser journey exercises wrong-code correction and successful setup behind forwarded headers. A proxy that strips every forwarding header must set the server's public URL to disable the local bypass.
- **LAN browser sending (R02/U03):** send keys use `crypto.getRandomValues`, which is available on plain HTTP LAN origins. A regression removes the secure-context `randomUUID` API and verifies that a real send still settles.

A password someone else chose now has to be replaced before the workspace opens (A02).
Schema v17 marks such a password, an admin reset sets the mark, and until its owner chooses
their own the account can reach only the password change and sign-out — enforced centrally in
`requireUser` so a route added later is covered, and on the socket handshake too, since
otherwise a temporary password still handed over the whole workspace. Login says so rather
than letting the client discover it by being refused, and the sign-in card asks for a new
password instead of going in.

lists the accounts; with `--handle` it issues a one-time password, ends that account's
sessions and requires a new password at next sign-in; `--make-owner` also hands the workspace
over, which is the way back from an owner who has left, with the previous owner stepping down
to admin rather than out. It works against the workspace file with the server stopped, so it
grants nothing that reading the file did not already, and it covers the case the API
deliberately refuses: the owner, whom no admin may reset. A deactivated account is revived
rather than recovered into a locked door. `packages/server/test/recovery.test.ts` adds seven
regressions, and the flow was exercised against the packaged server binary end to end.

`thread_follows`. Per-thread mute, mark-unread and a mentions-in-threads split remain
separate work. `packages/server/test/threads.test.ts` adds sixteen regressions; the browser
journey was checked with a disposable Playwright review.

Messages and replies can now be marked unread (C04). The chosen message and everything after
it becomes unread, in a channel or in one thread independently; marking a thread unread
follows it, since it is a statement of intent to come back. The hazard is that the timeline
acknowledges its own visible tail, which would read the message again a moment later, so a
marked conversation is held: automatic acknowledgement skips it, an acknowledgement already in
flight is abandoned and its echo ignored, and the hold survives a resync that discards loaded
history. Leaving the conversation lifts the hold, so returning reads it; Activity's "read
through here" is an explicit request and lifts it too. Read echoes now distinguish a cursor
advancing from one deliberately moved back, because the former is only ever applied as a
maximum. Thread unread counts no longer exclude your own replies — the cursor already records
that you have seen your own writing, and excluding them made marking one of them unread show a
badge with nothing behind it. `packages/client-core/test/unread.test.ts` adds six regressions
covering the hold, and the server suite covers the routes; the browser behaviour was checked
with a disposable Playwright review.

A reply can now be sent to the channel as well (C03). It stays a reply — it belongs to its
thread, counts toward its reply total, and opens there — but it also appears in the channel's
own timeline, marked as having come from a thread with a way through to it. What a channel
timeline contains is now defined once in the store and shared by paging, jumping and the live
tail, so those three cannot drift apart on it. The choice is per reply rather than a mode, it
is part of the send request's identity so a retry that changes it conflicts rather than
silently posting somewhere else, and it survives the outbox across a restart. Schema v16 adds
the flag. Asking for it on a message that is not a reply is ignored rather than refused.

Conversations now carry unread mention counts (C04). A direct mention counts anywhere; a
room-wide one only in a room, since `@here` in a direct message is just words. The condition
is shared with the Activity list, so a badge cannot disagree with what it opens. Counts travel
in the handshake snapshot and are recomputed and pushed only to the accounts a message names,
or to the one account whose own reading or mark-unread changed them. The sidebar shows a count
beside each conversation, and Activity shows the workspace total, taking precedence over the
plain unread-conversation count. Per-thread mute and mention counts scoped to a single thread
remain.

## Release acceptance criteria

A dependable small-team release should satisfy all of the following:

- Confirmed network interruption and acknowledgement loss do not lose or duplicate messages; replayed edits, deletes, and reactions converge on already-loaded views.
- Session revocation and private-channel departure remove live access and call participation; denial tests cover REST, sockets, files, integrations, and deep links.
- Drafts and outbox survive the documented lifecycle boundaries and remain isolated between accounts. A failed operation explains what happened and leaves recoverable work intact.
- Search, threads, files, and saved items remain accessible beyond their first page, with predictable navigation back to message context.
- A first-time host can claim, invite, stop/reopen, back up, restore, and upgrade a workspace using the UI/docs without editing application code.
- Core journeys work using keyboard alone and in narrow layouts. Media failure states are understandable, and supported network/device combinations have actual measurements.
- Data upgrades are tested against historical fixtures; release artifacts start successfully and preserve legacy data locations.
- Capacity claims include workload, duration, hardware/network, and limits. No universal latency, RAM, or call-size promise is inferred from a short localhost run.

### Workspace attachment quota (C07/F15)

Attachments now have a workspace-wide cap alongside the existing per-file one, closing the storage half of F15. The host sets it with `--storage-limit-mb` or `SLACKOSS_STORAGE_LIMIT_MB`; unset means unlimited, which stays the default. The budget counts what is already on disk at startup, so a restart neither forgets nor double-counts, and it reserves space as bytes arrive rather than after a file lands — otherwise simultaneous uploads would each be measured against the same free space and cross the line together.

An upload that would not fit is refused with `507 storage_quota_exceeded` and leaves neither a blob nor a reservation behind, so what still fits still fits. The same release runs when a file is cut off for exceeding the per-file limit, when access is revoked mid-upload, and when the blob cannot be removed — in that last case the id is queued for the existing cleanup worker, which releases it once the file is really gone. Deleting a message returns its attachments' space through that same worker.

Reserving per chunk means two uploads reaching the wall together can each hold part of the remaining space and both be refused, where either alone would have fitted. That is a deliberate trade against reserving the maximum file size up front, which would cap concurrent uploads at limit/maxFileSize however small they really are. Refusing is recoverable, so the property kept is that the limit is never exceeded.

`GET /api/storage` reports used, limit, available and per-file maximum. Account settings shows it to any member with retry on failure, and says plainly when the workspace is full; the composer and the outbox explain a quota refusal separately from an oversized file, keeping the draft either way. A cap lowered below what is already stored deletes nothing and reports no room rather than negative room.

`packages/server/test/storage.test.ts` adds nine regressions, and the flow was exercised against the packaged server binary. Abandoned-upload expiry, per-account quotas and streaming large downloads remain separate work.

### Abandoned uploads and orphaned blobs (C07/F15)

Uploads that were never sent are now freed, closing the other half of F15's file finding. An attachment chosen and then thought better of used to hold its bytes for the life of the workspace; with the storage cap in place that turned untidy into a workspace that slowly fills up. Unattached uploads older than 24 hours are swept on the same hourly cycle as the other retention work and once at startup, tunable with `--abandoned-upload-hours` or `SLACKOSS_ABANDONED_UPLOAD_HOURS`.

Files a scheduled message is still waiting to send are never swept, however old they are — a message queued a week out has attachments older than the window by the time it sends. The sweep reads the queue to find out which those are, and if a queue row cannot be read it does nothing at all that round rather than guessing: some unknown set of files is spoken for, and deleting an attachment on a guess is worse than reclaiming its bytes late. The window is validated as positive, since zero would sweep uploads as they land.

Blobs on disk that no `files` row accounts for are also reclaimed. A process killed between writing the bytes and recording them leaves exactly that: storage charged to the workspace that nothing would ever ask to delete. They are found once at startup — safe only there, since a blob being written right now has no row either — and go through the existing deletion queue so one that will not delete is retried rather than lost track of.

Both paths release their space through the same cleanup worker as message deletion, so the accounting has one owner. `--storage-limit-mb` and `--abandoned-upload-hours` now report a bad value by naming the flag rather than surfacing an internal option name in a stack trace.

`packages/server/test/storage.test.ts` grows to fifteen cases. The scheduled-message protection and the orphan reclamation were both checked by removing them and confirming their tests fail. Per-account quotas and streaming large downloads remain separate work.

### Durable integration event delivery (F16/R03)

Outgoing subscription events now enter schema v20's delivery queue in the same transaction as their workspace event. A queue-write failure rolls the mutation and event log back together. Delivery remains outside the user's request, preserves sequence order per subscription, and runs up to ten different endpoints in parallel. Each flush handles at most 50 events. Failures use increasing delays across eight attempts; pending work resumes at startup and runs every five seconds. HTTP responses outside 2xx count as failures. Successful rows are removed, while terminal failures remain for seven days so an administrator can see and retry them.

The event body and `event_id` stay stable across attempts; each attempt receives a fresh signature timestamp and Slack-compatible retry headers. This provides at-least-once delivery: a process exit after the receiver accepted an event but before completion was recorded can produce a duplicate, so receivers must deduplicate by `event_id`. Deactivated apps receive no new subscription events and their pending work pauses until reactivation. Deleting an app or subscription cascades its queue. Removing the bot from a channel atomically discards queued events for that channel, and delivery rechecks membership before every attempt.

Apps and integrations reports pending and terminal failure counts plus the latest error. Pending status refreshes while the dialog is open, and Retry failed makes terminal rows immediately eligible again. A disposable API review verified atomic rollback under an injected queue failure, strict ordering, restart recovery, stable bodies/IDs, retry headers and signatures, terminal retention/manual retry, app deactivation, subscription deletion, and private-channel revocation. The shared browser preview verified failed and pending states with no overflow. ### Bounding the integration delivery queue, and testing it (F16/R03)

The durable queue above had no ceiling. Delivery is ordered per endpoint, so a receiver that stops answering holds up everything behind it, and only the head is ever attempted; each event in turn had to spend the whole eight-attempt ladder — about eight hours — before the next one could start. A workspace that kept talking while an endpoint stayed down therefore grew that endpoint's queue without limit, every row holding a full event body, and an administrator who repaired the endpoint faced a backlog that drained one event every few hours.

Schema v21 adds a per-subscription tally of events that were never queued. One endpoint may now hold at most 500 waiting events; past that the event is counted as dropped instead, which is bounded and visible rather than silent. A delivery that exhausts its attempts now takes the rest of that endpoint's queue with it, since an endpoint that has used up a whole ladder is down and repeating that ladder per event only keeps a dead receiver under load. "Retry failed" restores the whole queue in order and remains the single way back. The dropped tally clears on the next successful delivery as well as on retry, so an endpoint that recovers on its own does not carry a warning for ever. Apps and integrations now reads "N waiting · N given up on · N dropped while behind".

The delivery work also had no permanent regressions. Seven now cover it: retrying a refused endpoint while later events wait behind it and carry Slack's retry headers; re-signing each attempt over a body and `event_id` that never change; giving up on a dead endpoint together with its backlog, with the events behind the head never attempted; an administrator retrying that backlog and receiving it in order; keeping retry to administrators and refusing a subscription that is gone; refusing to queue past the ceiling and reporting the drop, then clearing it on recovery; discarding queued events when the bot loses channel membership; and resuming an unfinished delivery in a second process on the same workspace file. Removing the backlog abandonment, the ceiling, or the tally clearing each fails its own case. Workspace typechecks, web/server builds, formatting and all 282 tests passed (server 196, client-core 58, UI 16, protocol 12). A configurable retry policy, per-endpoint circuit breaking before the ladder is spent, and a delivery history remain separate work.

### Revocation while an app is being used (I02)

Every capability handed to an app was checked when it was handed out and never again. A `response_url` lives half an hour, a `trigger_id` three minutes, an open form half an hour, and even an ordinary reply arrives only after the app's own endpoint has answered. In any of those gaps the app can be deleted or its bot deactivated, the bot can be taken out of the channel, the channel can be archived, and the person being answered can be deactivated or lose access — and none of it was noticed. An app deleted while it was answering still posted; a `response_url` kept posting rights for half an hour after the app it belonged to had gone.

One check now runs wherever a capability is spent rather than issued: the reply path shared by slash commands and button presses, the `response_url` route, `views.open` redeeming a trigger, and a form submitted long after it was opened. A `response_url` whose app, channel or audience has gone is deleted rather than merely refused, since keeping it would only invite the same call again.

Two of these were previously stopped, but by accident rather than decision: `postMessage` refuses a deactivated author and a channel the author cannot reach, so the reply failed deep inside and the command route caught it and told the person who typed the command that the app had not answered. It had; it was simply no longer allowed to. Those cases now return early, and the command reports success, because for the person who typed it the command did work.

Seven regressions cover it: an app deleted mid-request and one deactivated mid-request, each with the command still reporting success; a `response_url` spent once its channel is archived, once its bot is taken out of a private room, and once its app is gone, each refused as `expired_url` rather than failing further in; a trigger refused for a room that has since been archived, while the app is still installed and authenticated, so its token is not what stops it; and a form submitted after its room closed, which never reaches the app at all. Removing the check fails all seven. Workspace typechecks, web/server builds, formatting and all 289 tests passed (server 203, client-core 58, UI 16, protocol 12). Token and signing-secret rotation, scoped permissions, and bounding the in-memory trigger and response maps by count rather than only by expiry remain separate work.

### Rationing what one caller can do (A04)

Nothing bounded how often a caller could do anything. The cap on concurrent password derivations kept one burst from exhausting the machine, but a patient attacker was free to grind at a password all day, one attempt at a time, and nothing bounded messages, uploads, sockets or typing notices either.

A token bucket per caller now rations sign-in attempts, posting, uploads, opening a socket, and typing and call signalling. The design question that mattered was fairness to shared addresses: a workspace on an office LAN reaches the server from one NAT address, so a per-address limit tight enough to stop an attacker would lock out the whole company. Everything with an account to key on is therefore keyed on the account. Only the two things that have no account yet — sign-in and opening a socket — key on the address, and both are deliberately loose. What actually protects an account is a tight per-handle sign-in limit, and a loose per-address one still catches somebody spreading attempts across many handles to evade it.

Only failures count against the handle. A correct password clears what that handle has spent, as does registering it, so someone who knows their own password never meets this limit however often they sign in or changes it — the earlier version of this charged for success too, and locked a legitimate password change out of signing in. A refusal answers `429` with `Retry-After`, and costs nothing itself, so a client retrying too eagerly does not push its own recovery further away. Typing notices are dropped silently rather than answered with an error, since a lost keystroke indicator is not worth an error frame and certainly not worth the socket. Buckets are dropped once refilled, so the bookkeeping stays proportional to who is active rather than to everyone who has ever connected.

The defaults were set against real use rather than against what made tests pass. The posting burst is sixty because an outbox emptying itself after someone has been offline is a legitimate rush of writes that must not come back as a failed send, and the upload burst is twenty so a folder can be dropped in at once. Two existing suites did trip the limits, and both for the same reason: they build long channels by posting hundreds of messages in a loop from one account, which is precisely the flooding this refuses. Those suites now run with limits off, because what they test is client paging and route behaviour, and rationing has its own file where it is the subject rather than a background condition every other case works around. `--no-rate-limits` does the same for a host running an import or seeding a workspace.

Thirteen regressions cover it: the bucket's burst-then-refill, refusals costing nothing, callers kept apart, and buckets dropped once refilled; then guesses at one handle stopped with a `Retry-After` that is refused even when the password is finally right, a correct password never meeting that limit at all, one handle's guesses not locking out a colleague on the same address, an address spreading across handles still bounded, a flood from one account leaving both other people and its own reading alone, sockets from one address bounded, typing notices dropped without closing the socket, and nothing rationed when the host has turned limits off. Removing the enforcement fails five of them; the rest are unit-level or cover the gateway and the off switch. The browser suite seeds history the same way, five hundred messages in a loop against the packaged CLI, so it now starts that server with `--no-rate-limits` — which exercises the flag end to end as well. That suite runs against a built binary rather than the sources, so it has to be rebuilt before it means anything; a first run here passed only because it was still testing the previous build. Workspace typechecks, web/server builds, formatting, all 302 tests (server 216, client-core 58, UI 16, protocol 12) and all 7 browser scenarios against a freshly built CLI passed. The rest of A04 — allowed origins and trusted proxies, preferring the configured canonical URL for callbacks, a content-security policy, and redacting credentials and token-bearing paths from logs — remains separate work.

### Keeping credentials out of the log (A04)

Three of this server's URLs carry a working credential rather than an identifier: `/hooks/<token>`, whose token is an incoming webhook's entire authority and never expires; `/api/commands/response/<token>`, which is thirty minutes and five uses of the right to post as a bot; and `/api/files/:id?download=<ticket>`. Fastify logs the request URL, and the CLI turns logging on, so every one of those requests wrote a usable secret into the log — read by whoever can read the log file, and on a hosted deployment often shipped somewhere else entirely.

The ticket was already handled, by silencing logging for the file route altogether. That works, but it costs all visibility of file traffic and only protects routes somebody remembered to mark. Redaction achieves the same protection while keeping the log worth having, so the blanket silence is gone and the route is logged like any other: the shape of a request survives — which route, which file, which parameters were present — and only the values that would still work if copied are replaced.

Pino's `redact` covers headers as well. Fastify does not serialise headers by default, so nothing leaks there today, but that is a default somebody can change, and a redaction already in place when they do is worth more than one added afterwards. `logger` now also accepts a destination stream, which is both a reasonable thing for an operator to want and how the test reads back what was actually written.

The list of secret-bearing shapes needs maintenance: nothing detects a new token-carrying route automatically, so adding one is part of writing it, and the module says so where someone will see it. Query parameters are matched by name against a small set, so a token arriving as a query value is covered without being listed individually.

Eight regressions cover it, seven on the rewriting itself and one against a running server asserting that no webhook secret, response_url secret, download ticket or session token appears in what was logged, while the routes that were called still do. Removing the redaction puts the webhook secret straight back in the log. Workspace typechecks, web/server builds, formatting and all 310 tests passed (server 224, client-core 58, UI 16, protocol 12). Allowed origins, trusted proxies, preferring the configured canonical URL for callbacks, and a content-security policy are what remain of A04.

### Not believing what the network says about itself (A04)

Two things were taken on trust from headers anyone can write.

The URL handed to an app was built from `X-Forwarded-Host`, or failing that the `Host` header. That URL is a `response_url`: it carries a token and it is where the app posts its reply. Building it from a request header meant whoever sent the request chose where that reply went, so a forged header — no proxy involved, just a `Host` on an ordinary request — pointed the app at somewhere else entirely and sent the token with it. The configured public URL is now used when there is one, forwarded headers only when `--trust-proxy` says a proxy writes them, and otherwise the address the connection actually arrived on, which no header can change. On a machine serving a LAN that is the interface the client really reached, so it is the useful answer as well as the safe one.

The local bypass treated any request from loopback as the host's own. It is not: a web page somebody merely visits can have their browser post to localhost, and that request arrives from loopback like any other. While a workspace still had no owner, that let a visited page claim it without the claim code. A command line request carries no `Origin` at all, a browser always sends one on a write, and a page served from anywhere else names that somewhere else — so an `Origin`, if present, now has to be this same server, matched on host and port both, since another port on the same machine is another program.

Fifteen regressions cover it. Reverting either change fails its own cases, and the failure message for the first is the attack written out: `https://evil.example.com/api/commands/response/<token>`. One of them was passing vacuously at first because Node's `fetch` drops a `Host` header silently, so that case now issues the request through `node:http` and genuinely forges one. Workspace typechecks, web/server builds, formatting, all 325 tests (server 239, client-core 58, UI 16, protocol 12) and all 7 browser scenarios passed. A content-security policy and a considered origin allowlist are what remain of A04; the permissive CORS setting is deliberate for now, because the browser client is a static app that can be hosted separately from the workspace it talks to, and bearer tokens rather than cookies mean CORS is not what protects a session.

### A content security policy for both clients (A04)

The client has no inline scripts, no `innerHTML`, and no `eval`, so `script-src 'self'` costs nothing and is the directive that actually matters here: it means markup that arrives in a message cannot become running code, which is the failure a chat application is most exposed to, since its whole job is displaying text other people wrote. Objects are refused, the base URL cannot be rewritten, and the page cannot be framed.

`connect-src` is deliberately open, for the same reason CORS is. The browser client is a static app that can be pointed at any workspace — that is how somebody signs in to a server other than the one that served the page, and how one browser holds several workspaces at once. Narrowing it would break that rather than protect anything.

`Referrer-Policy: no-referrer` goes with it, and belongs to the same problem as the log redaction above: this server puts tokens in URLs, and a referrer would hand one to wherever a link led.

The headers go on every response rather than only on the client's HTML, since an API reply can be navigated to directly and a header that is always there cannot be forgotten on the one route that needed it. A route that set a header for itself keeps it. The desktop app loads its client from disk, where a response header cannot reach it, so the same policy is written into its renderer HTML — minus `frame-ancestors`, which a meta element cannot enforce and which browsers ignore there rather than failing, so writing it would read as protection that is not there. A test reads that file and fails if the two ever disagree.

Ten regressions cover the policy and the headers, and the seven browser scenarios now fail on a CSP violation as well as a page error, since a blocked resource is reported to the console rather than thrown and would otherwise have slipped past. That guard was checked by tightening `img-src` to `'none'` and confirming the suite names the blocked file. Adding the headers also broke one existing test — not the product, but a race in a test written earlier, which assumed a single `flushEventDeliveries()` call would be the one to make the next attempt when a flush already running is joined rather than restarted; it now loops. Workspace typechecks, web/server builds, formatting, all 335 tests (server 249, client-core 58, UI 16, protocol 12) and all 7 browser scenarios passed. The packaged desktop app could not be checked here — Playwright's Electron launcher fails on this machine, though the built binary starts by hand — so the meta policy is verified by CI's Windows job rather than locally.

### Verifying reconnect and resync, and one loop that never ended (R01)

Most of what R01 asks for was already built, and the audit for this entry is as much of the finding as the change is. The snapshot's high-water mark is separate from the last applied event, `synced` defines when replay is complete, replay overflowing its limit or falling below what pruning kept both return nothing and reset the client, visibility is filtered in SQL rather than assumed, drafts and the outbox survive a snapshot replacement, and channels that have gone are removed. Nothing assumes sequence numbers arrive consecutively: an event is ignored when its sequence is not ahead of what has been applied, rather than when it is not the next one. The ordering that makes registration safe — a socket joins the fan-out before its snapshot is built — holds only because every step between is synchronous, which is worth knowing before anyone puts an `await` there.

What was missing was evidence, in exactly the places the item calls risky. Four cases now cover them: a run of reconnections that must lose and duplicate nothing; a replay across a private room the account cannot see, which is what makes delivered sequence numbers non-consecutive, checked to leave the client caught up to where the server is rather than to the last thing it was shown, so the next reconnection does not walk the same gap again; a server that has gone backwards, where the client holds a cursor past anything the server still has and has to reload rather than wait for sequence numbers that will never come; and an account the server will refuse until its password is replaced.

That last one was a real defect rather than a characterisation. The gateway refuses a locked account and closes with its own code, but the client handled only the codes for a bad token and a version mismatch, so a locked account fell through to the ordinary retry path and reconnected for ever — every second, then every thirty, telling the person nothing except "reconnecting". Retrying only makes sense for a refusal that might stop; this one will not until somebody does something. It is now a terminal state of its own, which signs the person out, and signing out is what leads back to the screen that can replace a password, since signing in again lands on it holding the password it needs to replace. Removing the handling puts the loop straight back.

Workspace typechecks, web/server builds, formatting and all 339 tests passed (server 249, client-core 62, UI 16, protocol 12). The remaining parts of R01 — reconciling a huddle whose access ended mid-call, and a client that has been away longer than the event log for reasons other than pruning — are not covered here.

### What deleting means, and a retention window (A06)

Deleting a message removed it from the channel, the search index, the pins and the saves, and blanked its text in the messages table. It did not reach the copy of that text in the event log. Every message is written there too, so that a client which has been away can replay what it missed, and 20,000 of those events are kept — which on a small workspace is months. Someone who deleted a sentence had it removed from everywhere they could see and left, in full, in a file the host can read. Editing had the same shape: the first draft stayed. Taking back a sentence by editing it away is how most people do it, and leaving what it replaced on disk made the correction cosmetic.

The events cannot simply be removed. A missing sequence number looks to a catching-up client exactly like a log it has fallen off the end of, and sends it back for a whole new snapshot. So the events stay and their contents go: the message replays with nothing in it, followed immediately by the edit or the deletion that supersedes it, and the client lands where it would have anyway. Finding them needs an index — scanning 20,000 payloads on every delete is not a thing to do inside a request — so events now record which message they are about, backfilled from the payloads already stored. Attachment names go with the text, since a filename often says as much as the message it was attached to.

Retention is new and off by default, because a workspace that quietly started discarding history would be worse than one that grows. `--retention-days` turns it on, an hourly sweep removes conversation past the window outright rather than hiding it, and the window is printed on every start — a setting that deletes things is one to be reminded of. A thread ages out as one thing: a root is taken only once its newest reply is past the window too, because a reply hanging under nothing reads as a database that has gone wrong rather than as a policy doing its job. Nothing is announced to connected clients; these messages are old enough that no screen is showing them, and announcing a year of deletions would put the events into the very log this is meant to keep small. Two thousand threads go per pass so the first sweep does not hold the database for a minute.

Writing down what deletion means turned up one thing that was not what it looked like. Deleting a thread root drops the thread from the followed list and makes asking for it return `thread_not_found` — so deleting the message you opened a conversation with takes down everyone else's answers to it, while their rows and their words stay in the database, unreachable through the API but there on disk and in a backup. That is the one place where what a deletion appears to do and what it stores differ. It is now documented and pinned by a test rather than quietly changed: making the stored data match what people see would also be deciding that deleting your own opening message may delete other people's replies, and that is a product call rather than a cleanup.

`docs/DEPLOYMENT.md` now says what deletion reaches, one item at a time — the tombstone row, the replies, the attachments and the queue that retries their bytes, the pins and saves, the search index and the freed pages that `VACUUM` rewrites, the event log, the request log which never held message text, and backups, which still contain everything and which nothing this server does can reach into. There is no account deletion; deactivation ends sessions and stops sign-in, and what the account wrote stays.

Fourteen regressions cover it. Removing any of the four behaviours — redaction on delete, redaction on edit, redaction during the sweep, or the rule that keeps a live thread's root — fails its own cases; checked by taking each out and re-running. Workspace typechecks and all 353 tests passed (server 263, client-core 62, UI 16, protocol 12).

### Less motion, and typing that is not English (U07)

Three things, all of which only go wrong for people who are not the person who wrote the code.

The reduced-motion block shortened every animation to a hundredth of a millisecond. That works for a transition, which happens once. It does not work for a loop: the pulsing dot that says a call is live ran its whole cycle in that hundredth of a millisecond and became a flicker, which is worse for somebody who asked for less motion than what they were trying to avoid. Capping the iteration count is what ends it; the duration then only governs the one remaining cycle. Smooth scrolling is turned off in the same block, since that is motion nobody asked for either.

Enter means something different while an input method is assembling a character. Somebody typing Japanese, Chinese or Korean presses it to choose among the candidates their keystrokes produced, and a field that treats it as "do the thing" sends a half-written message with no way for the person to see that coming. The composer and the message editor both checked for this; the switcher and the search box did not, and both take Enter and do something irreversible with it — one jumps to another channel, the other runs a search. The check now lives in one place that all four call, and a test reads the four files and fails if any of them stops asking.

The third is about timing rather than about what a key means. Completing a mention or wrapping a selection in asterisks rewrites the whole field, which puts the caret at the end, so it has to be moved back. That move happened a frame later, in `requestAnimationFrame`. A frame is roughly sixteen milliseconds, and finishing a mention with Tab is exactly the moment somebody is typing fast, so a keystroke lands in the gap — and then the caret is dragged backwards out from under them and the rest of the sentence goes into the middle of a word they had finished. It now happens in a layout effect, before the browser paints, and is abandoned if the field has moved on in the meantime: leaving the caret where somebody's own typing put it beats moving it to where it belonged a moment ago.

Thirteen unit cases and two browser ones. The unit tests cover the rules; the browser ones cover the parts a pure function cannot reach — that the caret really does come back, and that the switcher really does ignore an input method's Enter. The first browser assertion was vacuous when written: it completed a mention at the end of the line, where the caret the browser leaves behind happens to be the right one anyway, so it passed with the restore removed entirely. It now bolds a word in the middle of a line, where the correct answer is a selection rather than the end, and fails without the fix. Workspace typechecks, formatting, all 366 tests (server 263, client-core 62, UI 29, protocol 12) and all 7 browser scenarios passed.

Interaction coverage in `packages/ui` is limited by there being no DOM test environment there — the tests render to static markup. The rules that can be extracted are tested directly, in the style the server uses for the same problem, and anything needing a live component goes to the browser suite. The rest of the U-series, U04 above all, will want jsdom and a component testing library before it can be held to much.

### Local work follows a workspace's identity (A03/C02/O03)

The authenticated ready snapshot now carries the workspace ID already persisted by the server. Drafts (including edits and replies), queued sends, scheduling recovery and recent searches use that ID plus the signed-in account ID. Older servers keep their existing URL/account storage. A changed account or workspace identity during an existing connection ends that connection before its local work can be applied to the replacement. Opening another session also remounts the workspace UI so component state cannot cross accounts at the same address.

Migration imports legacy data only when its stable slot is absent, checking the current address first and then previously approved addresses. This also recovers scheduling requests in thread composers that were never opened after upgrading at the old address. It writes the new copy before retiring the old key; explicit empty/null stable values remain authoritative, so cleared searches and dismissed scheduling requests do not return. Reads, migration and writes are serialized. Draft persistence captures its client and keys through asynchronous loading, switching and final lifecycle flushes. Failed reads retain intervening edits for retry; failed saves retry current memory instead of restoring stale work from disk. The outbox also preserves a reply's “also send to channel” choice through restart.

An ID supplied by a server is not proof that it owns the existing local work. Each account/workspace therefore remembers approved addresses. A previously unseen address claiming that identity shows both addresses and requires an explicit decision before mounting any local-work consumer or automatically sending its outbox. A first address is recorded before stable data is created. The shared browser review confirmed that an unapproved address has no composer and sends no queued message, and that approval restores the right account's draft and outbox.

Strict reads now distinguish unreadable storage from missing data. Malformed browser values remain intact and show a retryable error. Electron validates that settings contain a JSON object, leaves unreadable files untouched, rereads a repaired file on retry, and uses the same serialized atomic writer for hosting settings as other settings.

The shared browser additionally verified legacy draft/outbox/search/schedule recovery, address approval, account switching, malformed data preservation and repair, discarded sends staying discarded after a save retry, and cleared drafts staying cleared after a read retry. New permanent tests remain deferred at the user's request.

This does not move browser storage between web origins or profiles. Use the same installed desktop app or browser app origin to reuse local work across server addresses. ### Protected desktop sign-ins and recoverable credential storage (A03)

Electron now stores saved workspace sign-ins in a versioned, OS-encrypted envelope using `safeStorage`. The main process decrypts them for the existing client API. Reading an old plaintext list migrates it through the serialized atomic settings writer before returning credentials to the renderer. Other settings writes also migrate a legacy list before copying it, while an already encrypted list can be preserved without unlocking it. Empty lists need no encryption. A missing/locked key store or Linux's weak `basic_text` fallback never causes a new token to be written as plaintext.

Credentials that cannot be read are no longer treated as an empty account list. The app shows a recovery screen with Retry and a confirmed Forget saved sign-ins action; forgetting removes credentials only, retaining drafts, the outbox and hosted workspaces. Failed saves leave the current session usable with a retry notice. The latest in-memory list is what a save retry writes, and stale results cannot replace a newer navigation. Deep links arriving during a committed forget operation wait for it to finish. Error messages avoid quoting malformed JSON or decrypted credential contents.

Settings reads, migration and writes share one queue. Writes validate existing data, flush a temporary file and atomically replace the original; failures preserve the previous file. Replacing a nonempty encrypted list requires successfully reading its prior credentials, while an explicit empty-list reset works even after loss of the OS key. The shared UI validates saved-server records too, so malformed browser storage gets a recovery path rather than a crash or silent overwrite.

Validation: workspace typechecks, web/server/desktop builds, formatting, all 366 existing tests and all seven browser scenarios passed. Disposable backend checks covered migration, restart, concurrent writes, locked/failed encryption, malformed JSON/envelopes, failed atomic replacement, retry and selective forgetting. A native Windows probe used real Electron `safeStorage` in two separate processes to migrate, decrypt after restart, update and forget a fake sign-in; drafts survived and no plaintext credential copies remained. Shared browser checks exercised unreadable sign-ins, cancel/confirm forgetting, retry after repair, and a failed sign-in save that leaves the session open and later saves successfully. New permanent tests remain deferred.

This protects saved desktop credentials at rest, not drafts, message history, browser localStorage, old backups or a compromised running app/OS account. Existing plaintext credentials remain in the original file until migration can succeed. OS-key recovery and platform behavior differ; Linux and macOS runtime behavior was not exercised here. Browser session alternatives and broader settings recovery/export remain separate work.

The desktop credential work from the Codex session was reviewed and verified before merging. ### Replacing a leaked credential without deleting the app (I02)

An app has three kinds of secret — its bot token, its signing secret, and the secret in each webhook URL — and none of them could be replaced. The only remedy for one that had been pasted somewhere it should not have been was deleting the app, which also deleted its slash commands, event subscriptions, webhooks and interactivity settings, and created a new bot user in its place. There was a quieter version of the same problem too: the bot token is shown once, at creation, and stored only as a hash, so an administrator who closed the dialog before copying it had an app nobody could use.

Each can now be replaced from Apps and integrations, after a confirmation that says what will stop working. A new bot token replaces every token the app has, and the old one stops with that request. There is deliberately no overlap: a token is replaced because it leaked, and a window in which both work is a window in which the leaked one still does. A new signing secret applies to the next request the server signs — including event deliveries already waiting in the queue, since those are signed when they are sent, not when they were queued — so an endpoint whose secret leaked does not go on receiving events signed with it. A webhook keeps its id and its channel and gets a new URL; the old one returns 404. Each replacement is logged with what was replaced and by whom, never with the credential.

Keeping the old tokens, not storing the new secret, not replacing the webhook's hash, and dropping the administrator check each fail their own cases; the browser scenario fails if the new token is not shown. ### A copy before every upgrade (O02)

The server already refused a database newer than it understood, and each migration already ran in its own transaction, so a migration that failed left the old schema behind. What a transaction cannot undo is a migration that succeeds and turns out to be wrong, or an upgrade somebody wants to walk back a week later. Rolling back means the previous release together with the data it understood, and the documentation's answer — take a backup before upgrading — depended on somebody remembering to, every time, before the step that makes it too late.

The server now takes that copy itself. Before the first migration touches an existing workspace, `VACUUM INTO` writes a consistent snapshot, including anything still in the write-ahead log, into `pre-upgrade/` inside the data directory, named for the two schema versions it sits between. The copy is opened and its version checked before anything is migrated. The startup output says where it went and the log records it. A brand-new workspace, or one already current, gets no copy, since there is nothing to roll back. Only the three most recent copies are kept — each is a whole database — and anything else someone has put in that folder is left alone.

If the copy cannot be written, most often because the disk is full, the server refuses to upgrade: the error says nothing has changed, the file is still at its old version, and nothing is left holding it, which matters on Windows where an open handle would stop the host moving the workspace aside. `--skip-upgrade-backup` turns the copy off for someone who has just taken a backup and has no room for a second.

The copy is the database only. Attachments are not duplicated, since no migration touches them; the rollback instructions say what that means for anything uploaded after the upgrade, and that everything written since the upgrade is lost with a rollback.

Six regressions in `packages/server/test/upgrade.test.ts`. Taking no copy, not pruning, leaving the handle open on failure, swallowing a failed copy, and copying a workspace that is already current each fail their own cases. The open-handle case only bites on Windows, where CI runs it. The refusal case caught the opposite on Linux: removing the partial copy used `rmSync` with `force`, which ignores a missing file but not `ENOTDIR`, and on Linux a file standing where the copy's directory should be makes even that fail. Its raw error replaced the one saying nothing had changed. Windows reports the same path as missing, so the local run passed and CI's Linux job did not; the cleanup is now best effort. The bundled CLI was also started against a workspace one version behind, and printed where its copy went. Workspace typechecks, formatting, all 384 tests (server 281, client-core 62, UI 29, protocol 12) and all 8 browser scenarios passed.

Still open from O02: historical migration fixtures beyond the v8 one, and handling a disk that fills during the migration itself rather than before it.

### Settings refused at the door (O07)

A bad setting either crashed the server with a stack trace from inside Node or, worse, was accepted and quietly meant something else. `--port abc` and `--port 70000` failed inside `net.listen`, `--host 999.1.1.1` inside DNS, and an unknown flag inside the argument parser, each as a stack trace with no line saying which setting was wrong. `--retention-days 1.5` was announced at startup as 1.5 days and applied as 2, since the server rounds it. ### An honest integration contract, and the SDK it was not honest about (I04)

The Apps dialog tells an administrator that most existing Slack integrations work by changing the URL. Writing down exactly what the server supports, and checking each line against a running server, showed that for the most common way of building one — Slack's own SDK, or Bolt on top of it — that was not true.

Bolt calls `auth.test` before it will start, and gives up if the call fails. This server had no `auth.test`, so no Bolt app could start against it. Slack's SDK sends every call form-encoded, with anything that is not a plain value JSON-encoded into a string, so `blocks` and `view` arrived as text: a message posted through the SDK silently lost its buttons, and `views.open` could not open a modal at all. And a failed call answered with a 4xx status, where Slack answers with 200 and `ok: false`. The SDK's own source says it plainly — Slack's Web API does not use meaningful status codes besides 429 and 200 — and it reports any other status as a failure to connect without reading the body, so a bot checking for `channel_not_found` never saw it. Each of these was confirmed against the published SDK and Bolt source rather than recalled.

All three are fixed, along with the smaller things the same reading turned up. `auth.test` returns the bot's user id and the app's id, which is what Bolt reads to recognise its own messages. Structured arguments are accepted as JSON strings. Web API failures answer 200 with `ok: false`, and rate limiting keeps its 429 with `Retry-After`, which the SDK understands. A token is accepted as a `token` field as well as a bearer header, as Slack accepts it. A Slack method this server does not implement answers `unknown_method` by name instead of a bare 404, while the native API's own routes keep their not-found. ### A record of administrative changes (O05)

A workspace had no way to answer who deactivated someone, who promoted whom, or who replaced an app's token. Some of those actions wrote a line to the request log and most wrote nothing, and a request log is not somewhere an administrator can look.

Administrative changes are now recorded as they happen, in the same transaction as the change so neither exists without the other: role changes, deactivation and reactivation, password resets, handing the workspace over, recovery from the command line, apps and their credentials, webhooks, slash commands, event subscriptions and their retries, where an app's buttons and forms go, and invite codes. A change that changes nothing, such as setting a role someone already has, is left out, and so is one that was refused. Administrators read it newest first under People, where each entry is written as a sentence — "You deactivated frank", "Alice replaced Deploy Bot's bot token" — with names looked up when it is read.

The record never holds a credential. Tokens, signing secrets, passwords and invite codes stay out, and so do the URLs given to apps, which often carry a secret in their path; only the host is kept, and an invite is identified by a short fingerprint of its code, the same when it is created and when it is revoked so the two can be matched. A recovery made with the command-line tool is recorded with no actor, since nobody signed in did it. Entries are ordered by when they were written rather than by id, because ids made in the same millisecond are not ordered among themselves and two changes a moment apart must not read the wrong way round. The record lives in `workspace.db` and is not shortened by the retention window. `DEPLOYMENT.md` says plainly what it is not: tamper-proof evidence against someone who can read and write that file.

Recording nothing, recording a whole URL, recording an invite code, recording an unchanged role, and ordering by id each fail their own cases; the ordering case uses ten entries in one millisecond, where the first draft used three and would have passed by chance about a third of the time. Every recorded action is checked to read as a sentence both with all of its details and with none, which caught a sentence that printed "undefined" when a detail was missing. The deactivation browser scenario now opens the record and finds the entry. ### Checking a backup without repeating what the original did (C2, O01)

Ticket 6 of the roadmap's first sprint asked for a manual backup and a restore that can be tried in isolation, with the backup's outside dependencies listed and outbound work turned off at the destination. The command line already had `backup`, `verify-backup` and `restore`. What it lacked was a safe way to start the result. A restored copy holds the original's apps, their signing secrets, its queue of scheduled messages and its undelivered app events. Started normally to check it, the copy posts every scheduled message already due a second time and calls the same apps as the same workspace, and it announces itself on the local network under the original's name.

The server gained an `isolated` option, and the command line `--isolated`. An isolated start posts no scheduled message and delivers no app event. It refuses every request to an app with "this is an isolated copy of the workspace, which does not contact apps", which slash commands, buttons and forms already show to whoever used them. It does not announce itself over mDNS, and from the command line it listens on 127.0.0.1 unless `--host` is given. Nothing it holds back is marked failed or spends an endpoint's retry attempts. The same data started normally posts and delivers all of it, so the documented advice is to delete a checked copy rather than promote it. Every request to an app now goes through one function, which is where the refusal lives. A start bound to loopback no longer prints LAN addresses to "share with your team".

`verify-backup` now also lists what starting the backup would reach outside itself: each address its apps are sent events, commands or button clicks at, the scheduled messages waiting and when the first is due, app events not yet delivered, and how many sign-ins it would accept. That last count includes sign-ins ended after the backup, which a restore brings back. It reads a backup from an older schema without upgrading it. The settings a backup never holds, `--public-url`, `--retention-days`, `--storage-limit-mb`, `--allow-private-hooks`, `--trust-proxy`, `GATHERLINE_ICE_SERVERS` and whatever proxy sits in front, are printed with it and listed in DEPLOYMENT.md.

Two cases in `packages/server/test/backup.test.ts` use a stand-in app on loopback. The first lists a backup's app address with both of its uses, its waiting scheduled message, its refused event and its two sign-ins. The second restores into a fresh directory with that message and the event's retry already due. Started isolated, the copy posts nothing, a slash command fails without reaching the app, and a new message delivers nothing. Started normally, the same directory posts the message and delivers the held event. The second case fails when the copy is started without isolation. Every message in a channel was its own Tab stop, and so was every control inside it: the author's picture and name, links, reactions and, once a message had focus, up to fourteen toolbar buttons. Getting from the header to the composer with Tab meant passing hundreds of stops in a busy channel.

`useRovingMessages` in `packages/ui/src/lib/useRovingMessages.ts` makes the timeline one Tab stop, the current message. That is the newest until somebody moves. Only the current message and its own controls stay in the Tab order. The others' controls are taken out, and put back when their message becomes current. A mutation observer keeps this true as messages arrive, change and leave without the list rendering again. ArrowUp and ArrowDown move between messages, and Home and End go to the first and last. Enter goes into the message's actions, and Escape comes back out to the message. A control that uses Escape itself, such as the message editor, keeps it. Clicking into a message makes it current. Nothing changes for a pointer or for a screen reader's reading cursor, only the sequential Tab order.

Six UI cases cover the Tab stops, the keys, the editor keeping its Escape, clicking into a message, and new messages arriving. The keyboard journey now uses ArrowUp and Enter in a real browser. A thread's replies are not roving yet.

### A thread is one Tab stop too (U04)

The thread panel's root and replies now use `useRovingMessages` as the channel's timeline does. The newest reply is the thread's one Tab stop until somebody moves, and the arrow keys, Home, End, Enter and Escape work the same way. The keyboard journey checks that, after replying, the reply is the thread's one Tab stop and the root is out of the Tab order, and that ArrowUp moves from the reply to the root.

### The remaining compact controls explain themselves (U03)

The composer's buttons were one slice of replacing native `title` hints. The rest are done. The formatting toolbar, the huddle stage's Grid view, Expand video, Full screen and Hide video, its tiles and their Pin and Unpin buttons, the header's huddle button, a thread's Follow, an ephemeral message's Dismiss, Activity's Read through here, the sidebar's section actions and a saved workspace's Forget button now use the shared tooltip. A native hint shows only after a long hover, never on keyboard focus, and screen readers treat it unevenly. The tooltip opens at once on focus, is read as the control's description, and is dismissed with Escape. The formatting toolbar's hints name the shortcuts the composer and editor already had: Ctrl/Cmd+B, Ctrl/Cmd+I and Ctrl/Cmd+E. Strikethrough and a code block have none, and their hints claim none.

Two buttons shown only on hover could take focus while invisible. Dismiss was transparent, and Forget this workspace was hidden with `display: none`, so the keyboard could not reach it at all. Both now show on keyboard focus.

The browser suite found one place a tooltip does harm. On a narrow window, opening the navigation drawer puts focus on the sidebar's Jump button. A tooltip there opened unasked and took the Escape meant to close the drawer, which stayed open. That button already shows its words and its shortcut, so it gets no tooltip. It dropped its native hint and gained `aria-keyshortcuts`. The rule this leaves: a control that receives focus by itself when something opens should not carry a tooltip.

Native `title` hints stay on text that truncates, such as a workspace's address and a huddle's channel, on an image preview's file name, and on status icons such as Muted and Huddle in progress, whose accessible names already say the same. `Menu.tsx`, `Dialog` and `Modal` pass `title` as a heading, not as a DOM hint.

Four UI cases in `packages/ui/test/controlTooltips.dom.test.tsx` cover it:

- each formatting button names itself and its shortcut on focus, with no native title, an axe check, and formatting still working by key and by click
- the emoji button still gets focus back when its chooser closes, through the ref the tooltip wraps
- the huddle stage's controls say what pressing them does now without renaming them, and a tile says it shows that person large, with an axe check
- the header's huddle button is named by its tooltip when its word is hidden on a narrow screen, and follows the count

All four fail against the old components. Two browser scenarios found the huddle button by its native title and now find it by role and name.

### The conversation someone last had open (U02)

Starting the app with nothing in the address or history landed in #general every time, so anyone who lives in another channel or a direct message had to find it again. The app now remembers the open conversation for each workspace and account on this device, and opens it the next time nothing says where to be. It is kept by `useLastConversation` in `packages/ui/src/lib/lastConversation.ts`, under the same workspace-scoped keys drafts and recent searches use, so two workspaces, or two accounts in one, never share it. Nothing was saved under an address before workspace IDs existed, so it has no older slot to migrate from.

An address, a history entry or a link to a message still decides first. The workspace screen waits for the saved value before choosing, and a value that is empty, malformed or unreadable counts as none, so a broken store costs a click, never a blank screen. A remembered conversation that has gone, been archived or cannot be seen falls back to #general. The restored conversation replaces the page's history entry, so Back leaves the app rather than stopping in #general. Only the conversation is remembered, not a thread or panel beside it: the address already keeps those for a reload, and reopening a panel on a fresh start would be a surprise.

Four UI cases cover the hook, and each guard fails one when removed. The route browser scenario opens a second tab with nothing in the address and lands in the conversation last open, with Back leaving the app, then archives it and lands a third tab in #general.

### One Account settings dialog (U02)

Your own account was spread over three places. A profile dialog sat behind the sidebar's avatar. Account settings, behind the Workspace menu, stacked composing, the password, devices, signing out and storage in one long scroll. Browser notification permission was offered only by a banner that stays away for two weeks after Not now, with no way back to it.

Account settings now holds all of it, a section at a time: Profile, Notifications, Composing, Security, Devices and Storage. The sections are tabs. The arrow keys, Home and End move between them, both axes work because the list stands in a column on a wide window and runs in a row on a phone, and only the chosen tab is a Tab stop. The sidebar's avatar opens the dialog at Profile. The profile form, `ProfileForm`, now saves in place and says "Profile saved." instead of closing, and a change after that clears it. Security holds the password and signing out of the workspace, and Devices the signed-in devices. An error, a notice or a waiting confirmation belongs to the section it came from and goes when another is chosen.

Notifications is new. It says what this browser allows. If the browser has not been asked, it offers to turn notifications on. If it refused, it says where to allow them, since a page cannot ask twice. The desktop app shows its own, so there it says so and asks nothing. The section also pauses and resumes notifications for the account, with the same choices as the sidebar, whose wording moved to `packages/ui/src/lib/snooze.ts` so both say the same thing. Nine UI cases in `packages/ui/test/accountSections.dom.test.tsx` cover the tabs, the keys, opening on a named section, a confirmation left behind, the profile saving in place and the notification states, and four guards each fail a case when removed. ### Switching workspace from the top of the sidebar (U02)

Switching workspace took the Workspace menu, then Switch workspace, then a pick from the sign-in screen's list, which closed the open workspace first. The workspace's name at the top of the sidebar is now a menu of this device's other saved workspaces, most recently used first. ### Settings and list dialogs in the address (U02)

Account settings, People, Apps, Invite people, Keyboard shortcuts and Channel details were invisible to the address. A reload closed them, Back left them open and went somewhere else, and nothing could link to one. The address now names an open dialog after the conversation, thread or panel beneath it, and Account settings' section after that: `#/c/<channel>/p/saved/d/account/security`. Forms, pickers, search and someone's profile stay out of the address: they are passing moments, and reopening a half-filled form on reload would surprise more than help. People and Apps close for anyone who is not an administrator, whatever the address names, and rewrite the entry as they go. `writeRoute` now says whether it added a step, rewrote the entry or had nothing to do, which is how the screen knows a dialog's step is its own. ### A phone's Back closes the navigation drawer (U02)

On a phone, the navigation drawer was invisible to history, so the system Back button left the conversation behind the drawer instead of closing it. Opening the drawer now adds a history step, kept in the entry's state and never in the address, since the drawer is not a place to link to. Closing it without going anywhere, by Back, Escape, the backdrop or the window growing out of the drawer layout, goes Back through that step. Choosing a conversation, panel or dialog from the drawer takes the step's place, so Back from there returns to where things were before it opened. Escape with the drawer open now closes only the drawer, where it used to close a panel behind it too. An entry's open drawer reopens only while the sidebar is a drawer, so a wide window never ends up with an inert page and no drawer.

### Back returns to where a conversation was being read (U02)

Back, Forward and a reload returned to the right conversation but always at its newest message, so someone reading back through a long channel lost their place whenever they looked at something else. The timeline now notes, as the reader scrolls, which message is at the top of the view and how far down it sits. The note goes in the history entry for that conversation, through `rememberReadingPosition` in `packages/ui/src/lib/route.ts`, without adding a step or changing the address. It is written a moment after scrolling stops, and again when leaving the conversation or the page, and only ever to an entry showing that conversation, so a late note cannot land on the entry for somewhere else. Arriving by Back, Forward or a reload puts that message back at the same height once it has rendered. Opening a conversation from the sidebar makes a new entry and still starts at the newest message.

If the conversation loads without that message, because it is older than what a fresh load brings, the view starts at the newest rather than fetching far back on its own. A thread's scroll position is not kept yet; that belongs with C03.

Three route cases cover noting and reading positions, and the route browser scenario scrolls a long channel halfway and checks that Back and a reload each return to the same message at the same height. Without the timeline change it fails where the position should be noted. With this, U02 is mostly done.
